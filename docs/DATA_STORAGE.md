# 데이터 저장량과 보관 기준

운영용 웹소켓 프로필은 실제 매매에 쓰는 자료와 진단용 사본을 구분합니다. 다음날 전략 준비·재시작·매매 기록 조회에 필요한 자료를 유지하면서, 같은 상태를 매 처리마다 큰 이력으로 반복 저장하는 양을 줄입니다.

## 무엇이 달라지나

| 자료 | 운영용 저장 방식 | 보존하는 이유 |
| --- | --- | --- |
| 주문·체결·손익·금융 장부 | 이번 용량 제한에서 제외 | 잔액·보유 수량·매매 이력을 복구해야 합니다. |
| 주문에 연결된 종목 선정 근거 | 해당 선정 기록 전체 보존, 진단 한도에서 제외 | 주문의 `selection_id`로 당시 판단을 확인합니다. |
| 최신 후보·종목 선정 화면·재시작 상태 | 기존대로 매 변경 반영 | 이력 저장 간격이 화면 갱신이나 매매 판단을 늦추지 않습니다. |
| 당일·과거 분봉, 호가 원본, 뉴스 원본·분석 | 기존 수집·보관 정책 유지 | 전략 계산, 분봉 복구, 뉴스 화면과 다음날 운영에 사용합니다. |
| 주문 없는 일반 종목 선정 이력 | 최대 1분에 1건 | 매 처리마다 같은 큰 판단표를 이력으로 저장하지 않습니다. |
| 엔진 진단 표본 | 일반 처리 최대 1분에 1건, 주문 호가 검사 시 우선 기록 | 지연·주문 문제를 조사할 자료를 제한적으로 남깁니다. 우선 기록도 당일 한도를 적용합니다. |
| 뉴스·시장 상태 등의 재현용 사본 | 운영 프로필에서 추가 저장하지 않음 | 원본 테이블과 최신 상태에 이미 저장됩니다. |

일반 선정 이력과 엔진 진단은 **미국 동부 날짜별 합계 128 MiB 또는 5,000건** 중 먼저 도달하는 한도를 공유합니다. 개별 표본은 **512 KiB**까지이며, 초과 표본은 생략합니다. 합계는 직렬화한 JSON 크기이고 인덱스·여유 공간을 포함한 DB 파일 크기가 아닙니다. 주문에 연결된 선정 근거 등 필수 기록은 합계에서 제외하므로 **DB 전체의 최대 크기를 보장하는 제한은 아닙니다.**

한도와 저장 개수는 DB에 보존하므로 재시작해도 같은 날의 한도가 초기화되지 않습니다. 한도 상태가 잘못됐거나 시계가 이전 날짜로 이동한 경우에는 보조 표본을 추가 저장하지 않고 필수 장부 처리를 유지합니다. 기록 저장 자체의 DB 장애는 기존 트랜잭션 오류 처리 대상입니다.

시스템·설정의 **보조 기록 저장량**에서 마지막 저장 날짜, JSON 용량, 건수와 한도 도달 여부를 볼 수 있습니다. 화면 조회는 저장된 작은 상태 하나만 읽고 전체 테이블 집계를 실행하지 않습니다.

시스템·설정의 처리 기록은 최근 최대 100건의 결과 요약만 DB에서 조회합니다. 종목별 상세 근거가 담긴 전체 JSON은 접힌 창에서도 브라우저에 전송하지 않습니다. 원본 기록과 주문 연결 근거는 DB에 그대로 보존합니다.

## 연구용 완전 기록과의 차이

`config/sessionquant.strategy-lab-websocket.example.yaml`에는 `auxiliary_storage.mode: bounded_diagnostics`가 적용됩니다. 별도 설정 파일을 사용한다면 이 항목도 명시해야 합니다. `full`이 기본값이며 기존 연구용 프로필은 완전 기록을 유지합니다.

운영 진단 표본에는 생략된 입력이 있으므로 하루 전체를 정확히 재현하는 전략 백테스트에 사용할 수 없습니다. 내보낸 묶음의 품질 보고서에 이를 표시하고 재생을 거절합니다. 완전 재현 연구가 필요할 때는 별도 연구 장부에서 `full` 프로필을 사용하세요. 대시보드의 체결·손익 이력은 필수 장부를 사용하므로 이 표본 제한과 별개입니다.

## 기존 용량은 언제 줄어드나

이번 변경은 **앞으로 생성되는 보조 기록**을 제한합니다. 기존 데이터에 대량 삭제나 테이블 재구성을 실행하지 않습니다.

시작·업데이트 때 남은 대상이 확인되거나 장 마감 후에는 검증된 백업을 확보하고 보관 정책에 해당하는 오래된 보조 자료를 정리합니다. 주문 연결 근거와 필수 장부는 보호합니다. 오래된 논리 데이터가 줄면 이후 SQL 백업 크기가 줄 수 있지만, InnoDB의 파일은 삭제한 공간을 재사용하며 운영체제에 바로 반환하지 않을 수 있습니다. 따라서 `du`의 DB 용량과 다음 백업 파일의 크기를 함께 비교해야 합니다.

시작 시 확인·건너뛰기·재개 조건은 [GCP 운영 안내](GCP_PAPER.md#시작업데이트-전-남은-자료-확인)를 참고합니다. 정리를 생략해도 코드 업데이트 전에 새 백업이 필요할 수 있습니다.

정리는 삭제 전에 보존 대상과 날짜를 확인합니다. 과거의 큰 JSON 때문에 조회가 시간 초과되면 묶음을 나누며, 한 건까지 줄여도 실패한 경우에는 같은 기록을 한 번 더 확인합니다. 이때 SQL 시간 제한은 남은 정리 시간 내에서 최대 10초로 설정합니다. MySQL의 실제 취소 완료 시점은 I/O 상태에 따라 늦을 수 있습니다. 재조회도 실패하면 해당 기록을 건너뛰거나 확인 없이 삭제하지 않고 중단합니다. 보고서의 `single_read_retries`, `last_single_read_retry`, `last_read_timeout`에서 재시도 횟수·결과·조회 제한을 확인할 수 있습니다. 이 복구 절차가 전체 잔여 자료의 정리 완료나 운영 DB의 속도를 보장하지는 않습니다.

다음 운영에서는 시스템 설정의 보조 기록 사용량, 정리의 삭제 건수·남은 대상, 백업의 DUMP/PACKAGE 시간과 최종 파일 크기를 확인합니다. 1분 표본 변경의 효과는 합성 검사에서 검증했으며, 실제 하루 절감량과 백업 시간은 운영 결과로 확인해야 합니다.
