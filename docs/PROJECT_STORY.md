# 프로젝트가 바뀌어 온 과정

SessionQuant는 **사람이 매매 규칙과 화면을 기획하고 OpenAI Codex와 함께 구현·수정하는 AI 바이브 코딩 프로젝트**다. 처음에는 미국 페니스탁의 빠른 움직임을 활용하려 했고, 지금은 미국 대형주를 대상으로 기획한 전략·LLM 활용·모의매매가 실제로 연결되는지 확인하고 있다. 저장소 이름 `pennyquant`는 처음 목표의 흔적이다.

현재의 성공 기준은 세 가지다. 정해 둔 조건으로 신호가 생기는지, LLM의 설명과 뉴스 분석 근거가 보이는지, 그 신호가 주문·체결·매도 기록으로 의도대로 이어지는지다. 실제 시세를 사용해도 주문과 잔고는 모의 장부에 기록한다. 수익성과 장기간 운영 안정성은 별도 검증 대상이다.

현재 실행은 [전략 실험 안내](STRATEGY_LAB.md), 설치와 운영은 [문서 안내](README.md)를 기준으로 한다. 이 문서는 변경 이유를 설명하며 과거 복구 명령을 실행하도록 안내하지 않는다.

## 계획을 조정한 이유

| 이전 계획·구성 | 실제로 확인한 제약 | 선택한 방향 |
| --- | --- | --- |
| 저가주 급등·급락을 빠르게 포착 | 빠른 가격 변화에 비해 확보한 시세·분봉과 조회·처리 방식으로 검증 가능한 범위가 좁았다. | 먼저 S&P 500 대형주로 좁혔고, 현재는 토스 제공 미국 상장 주식 중 시총 확인 후보 50개를 하루 고정한다. 확정된 5분·15분봉을 사용하는 비교적 느린 장중 전략이다. |
| 시총 후보 100개·집중 20개 | 종목마다 필요한 자료를 순환 조회하면 전체 갱신에 시간이 걸렸다. | 후보 상한을 50개로 줄였고, 새 전략 실험은 집중 10개를 관찰한다. 시총 미확인 종목을 제외하므로 50개가 항상 채워지는 것은 아니다. |
| 여러 전략과 많은 시장·거래량 조건을 마련 | 전략 코드가 있어도 모든 조건을 동시에 확인할 자료가 없으면 진입이 막혔다. 네 전략을 동시에 운영한 것이 아니라 선택한 한 전략을 실행하는 구조였다. | 새 실험은 **상승 → 조정 → 반등**의 단순 눌림목 하나에 집중한다. 기존 전략과 장부는 비교용으로 보존한다. |
| 모의매매에도 실제 계좌의 거래·소수점 자격 증명 요구 | API의 일반 소수점 주문 지원과 특정 계좌·종목의 거래 자격은 달랐다. 필요한 조회 근거를 확보하지 못해 모의매매도 대기했다. | 실제 계좌 권한과 모의 거래 가정을 분리했다. 현재 Paper 프로필은 가상 소수점 거래를 가정하되 상장 상태·알려진 제한·시세·잔액·위험을 계속 검사한다. |
| 과거 20일 같은 시간대 거래량과 비교하는 RVOL 필수 | 분봉 누락, 분할 전후 거래량 비교 근거 부족, 당일 자료 갱신 지연이 있었다. 계산값이 존재하는 것과 매매에 쓸 수 있는 것은 달랐다. | 기존 프로필은 자료 부족 종목 제외·검증 구분을 유지한다. 새 단순 눌림목은 RVOL을 필수 진입 조건에서 제외했다. 누락을 0으로 채워 통과시키지는 않는다. |
| 시장 ETF·업종·거시 분석까지 폭넓게 반영 | 관측 가격이 있어도 신선도·비교 기준을 확인하지 못하면 분석할 수 없었다. 설명이 많아 화면에서 현재 상태를 파악하기도 어려웠다. | 새 실험은 시장 ETF 강세를 필수 조건에서 제외하고 핵심 전략을 먼저 확인한다. 참고 자료와 매수 조건, 간단한 홈과 상세 진단을 구분한다. |
| 주기마다 종목별 REST 호가 조회 | API 요청 대기뿐 아니라 DB 반복 조회·저장과 동기 처리 때문에 다음 분봉 조회가 밀렸다. | 반복 DB 작업·저장량을 줄이고 처리 시간을 계측한다. 별도 웹소켓 프로필은 호가를 수신한 뒤 필요한 종목의 최신값을 묶어서 엔진에 전달한다. |
| 로컬 PC를 장중 내내 실행 | 야간 PC 운영과 모바일 확인이 불편했다. | GCP 서버 한 대에 프로그램·MySQL을 두고 VM과 매매 시작은 수동, 폐장 후 저장·백업·VM 종료는 자동으로 구성했다. |

현재 단순 눌림목은 최근 확정 15분봉의 상승, 1~4개 조정봉, 직전 고가 위에서 마감한 반등봉을 확인한다. 집중 목록은 개장 기준 30분마다 거래대금 순위로 재선정하며, 유효한 조정·반등 패턴은 유지한다. 정확한 하락 폭·위험·주문 조건은 [전략 규칙](STRATEGY_LAB.md)과 [예시 설정](../config/sessionquant.strategy-lab.example.yaml)을 따른다.

초기 품질 조건은 [당시 시장 데이터 기록](archive/stages/STAGE02_MARKET_DATA.md), 현재 모의 거래 가정은 [Paper 정책 코드](../sessionquant/market/paper_policy.py)에서 구분해 볼 수 있다.

**개장 후 75분 기준은 남아 있다.** 현재 지표에 당일 5분봉 15개가 필요하기 때문이다. API가 75분을 기다리라고 요구하는 것은 아니며, 재시작 시각부터 새로 75분을 세는 것도 아니다. 이 시간이 최적이라고 검증된 것은 아니다.

## 뉴스와 LLM도 구분해서 확인한다

뉴스 수집 성공, LLM 요청 성공, 응답 형식·원문 근거 검증 통과는 서로 다른 단계다. 검증을 통과한 답변도 분류가 정확한지는 원문과 대조해야 한다. 뉴스는 후보 순위의 보조 가점이고, 전략 설명 LLM은 시장·전략·매매 결과를 설명한다. LLM이 주문 API를 직접 실행하지 않는다.

또한 GDELT에서 기사 링크를 발견했다고 모든 언론사 본문을 가져오는 것은 아니다. 본문 취득·사용 근거가 설정된 소스와 실제로 확보한 본문만 분석하며, 제목만 있는 기사는 건너뛰는 정책을 유지했다. 따라서 기사 수신 건수와 실제 분석 건수가 크게 다를 수 있다. 이 제약과 호출·비용 확인 방법은 [뉴스·AI 설정](reference/NEWS_SETUP.md)에 정리했다.

## 운영 중 겪은 문제와 확인한 사실

| 문제 | 확인한 사실 | 이후 조치·남은 확인 |
| --- | --- | --- |
| 초기 VM 응답 지연과 파일시스템 복구 | 사용자 제공 검사에서 ext4 오류가 있었고 저널 복구 후 재검사는 정상으로 끝났다. | DB 확인과 백업·새 운영 환경 복구를 진행했다. **최초 오류가 발생한 원인까지 확정한 것은 아니다.** 뒤에 발생한 공간 부족을 이 장애의 원인으로 소급하지 않는다. |
| 장 마감 백업 실패: 공간 부족 | MySQL 디렉터리 약 13GB 중 실제 데이터베이스는 약 767MB, 변경 기록인 binlog가 약 12GB였다. 20GB 디스크 사용률이 99%였고 `no space left on device`가 기록됐다. | 단일 모의 DB 용도에 맞게 binlog를 끄고 압축 백업·여유 공간 검사·실패 표시를 추가했다. 서버가 꺼졌다는 사실만으로 백업 성공을 판단하지 않는다. |
| 다른 날의 백업 시간 초과 | 디스크 여유가 있는 상태에서 백업이 480초 제한에 걸려 중단됐다. 앞선 공간 부족과 별개였다. | 백업 단계별 시간·실패 기록, 30분 백업 제한과 바깥 종료 제한을 맞췄다. 장 마감 성공 기록과 복원 가능 여부는 계속 확인한다. |
| 장중 높은 CPU·오래된 종목 자료 | 높은 CPU 사용률과 함께 DB 요청·엔진 저장에 많은 시간이 쓰인 기록이 있었다. RVOL 산술 계산만으로 전체 지연을 설명할 수 없었다. | 사양을 조정하고 반복 작업·수집 순서·화면 조회량을 개선했다. 서로 포함되는 작업 시간을 합산하거나, 한 번의 측정으로 장기 성능을 보장하지 않는다. |
| 휴대폰 화면 끊김·검은 로딩 화면 | Cloud Shell 미리보기·SSH 터널·브라우저 연결은 VM의 매매 프로그램과 별도다. | 화면 주소와 연결 설정을 확인한다. 터널을 닫는 것과 systemd로 실행 중인 프로그램을 종료하는 것을 구분한다. |

공간 부족과 백업 시간 초과의 근거·복구 주의점은 [저장 공간 장애 기록](GCP_STORAGE_RECOVERY.md), 현재 배포·백업·종료 절차는 [GCP 운영 안내](GCP_PAPER.md)에 있다. 위 표는 운영 출력을 정리한 것이며 모든 장애를 하나의 원인으로 설명하지 않는다.

## 웹소켓으로 해결하는 것과 계속 필요한 것

웹소켓 프로필은 서버가 보내는 호가를 받아 후보별 반복 REST 조회를 줄인다. 수신 메시지마다 DB에 저장하거나 전략을 재계산하지 않고 집중 종목·보유 종목의 최신값을 묶어서 전달한다. 연결이 끊기거나 호가가 오래되면 신규 매수를 막고, 기존 보유의 위험 관리는 별도로 계속한다.

**웹소켓은 과거 분봉이나 누락 거래량을 복구해 주지 않는다.** 분봉·거래대금·상장 정보는 REST를 사용하고, DB·엔진이 느리면 웹소켓 수신 이후의 처리도 밀릴 수 있다. 구독 성공만으로 매매 준비가 완료되는 것도 아니다. 기존 REST 프로필은 유지하며 별도 장부로 전환·확인한다. [웹소켓 범위와 전환](WEBSOCKET_ROLLOUT.md), [호가 수신기](../sessionquant/collectors/toss_quote_feed.py), [실행 연결](../sessionquant/session_runtime.py)에서 경계를 확인할 수 있다.

화면은 이 과정을 **관측 가격 → 현재 전략 단계 → 대기 이유 → 모의 주문·체결**로 보여준다. 자동 검사는 정해 둔 입력에서 코드가 의도대로 동작하는지 확인하고, 장중 기록은 실제 데이터에서 그 흐름이 이어졌는지 확인한다. 두 결과를 구분해서 남기는 것이 이 프로젝트의 진행 방식이다.

과거 단계별 요구사항·완료 기록은 [보관 문서 안내](archive/README.md)에 있다.
