# 기획과 문제 해결

SessionQuant는 **“내가 기획한 프로그램을 Codex와 함께 만들어 실제로 동작시켜 보는 것”**을 목표로 한 개인 프로젝트입니다. 높은 수익률보다 정한 매매 전략, 실행 중 LLM 활용, 의도한 동작의 확인을 중요하게 봅니다.

이 문서는 대화에서 기획자가 직접 문제를 제기하거나 방향을 제안한 사례와, 그에 따라 구현한 내용을 구분합니다. AI가 찾아낸 세부 원인이나 구현 방법까지 기획자가 직접 설계한 것처럼 표현하지 않습니다.

## 처음 기획에서 현재까지

초기 이름은 PennyQuant였습니다. 미국 소형주의 빠른 움직임과 뉴스를 활용하는 넓은 범위의 매매 프로그램을 구상했습니다. 실제 시세를 연결한 뒤 API 요청 제한, 분봉 확보·처리 시간, 종목별 뉴스 부족 등의 제약을 확인했습니다.

중간에는 S&P 500 대형주 중심으로 범위를 줄였습니다. 현재는 토스에서 제공하는 미국 상장 주식 중 시총을 확인할 수 있는 종목을 최대 50개 골라 하루 동안 유지합니다. 그중 최대 10개를 집중 감시하며 단순 눌림목 전략을 평가합니다. 이는 공급자 자료 범위 안의 선정이지 미국 전체 시총 순위의 완전한 복제는 아닙니다.

**여러 조건을 가진 프로그램을 만들었다는 사실보다, 정한 규칙이 왜 실행되거나 대기하는지 설명할 수 있어야 한다**는 방향으로 정리했습니다.

## 직접 제안한 개선

아래 발언은 대화의 뜻을 짧게 요약한 것입니다. 코드의 세부 기준·예외 처리·자동 검사는 Codex와 함께 구체화했습니다.

### 1. 매매 전략을 이해할 수 있게 단순화

- **문제 제기:** “매매 시간도 짧고 조건도 많다. 수익률보다 내가 정한 전략대로 매매됐는지가 중요하다.”
- **제안한 방향:** 핵심 전략과 의도한 실행을 확인하는 데 집중하고, 복잡한 조건을 줄입니다.
- **구현:** 상승 → 1~4개 봉 조정 → 확정봉 반등의 단순 눌림목을 중심으로 구성했습니다. 과거 20일 거래량 비교와 시장 ETF 강세는 현재 프로필의 매수 필수 조건에서 제외했습니다.
- **남긴 기준:** 최신 호가·당일 분봉·잔액·손실 한도는 계속 검사합니다. 현재 당일 지표 계산에 필요한 개장 후 75분 조건도 유지합니다.

### 2. 종목 수와 교체 주기를 함께 조정

- **문제 제기:** “집중 5개에서 눌림목이 자주 나올까? 추세를 보다가 5분 뒤에 목록에서 빠지면 어떻게 하나?”
- **직접 제안:** 집중 종목을 10개로 늘리고, 개장 기준 30분마다 갱신합니다. S&P 500에만 한정하지 않고 미국 상장 회사의 시총을 기준으로 후보를 고릅니다.
- **구현:** 확인 가능한 시총 후보 최대 50개는 거래일 동안 고정합니다. 집중 목록은 거래대금으로 재선정하되 유효한 조정·반등 관찰과 보유·미체결 관리를 구분합니다.
- **주의점:** 집중 종목 선정은 매수 신호가 아닙니다. 자료가 없으면 목록이나 주문을 억지로 채우지 않습니다.

### 3. 순차 시세 조회 문제에서 웹소켓 검토로

- **문제 제기:** “무조건 순차 조회밖에 없나? 토스 API의 웹소켓을 쓰면 안 되나? 후보 50개를 모두 구독하면?”
- **구현:** 기본 후보와 위험 관리 종목의 호가를 웹소켓으로 받습니다. 최신값을 모아 엔진에 전달하고 연결이 끊기면 재접속·구독 변경을 처리합니다.
- **Codex가 구체화한 부분:** 재접속 전 오래된 호가를 새 주문에 쓰지 않기, 같은 신호로 중복 주문하지 않기, 호출·처리량 제한과 자동 검사.
- **남은 제약:** 웹소켓이 매매용 과거 분봉을 채워 주지는 않습니다. 분봉은 REST 조회이며 API·DB·계산 중 어디서 늦는지 다음 운영에서도 확인해야 합니다.

### 4. 휴대폰에서도 이해할 수 있는 대시보드

- **문제 제기:** “표가 너무 단순하고 어렵다. 메인 화면은 간단해야 한다.”
- **직접 제안:** 종목별 상승·조정·반등 단계, 티커 아래 한글 이름, 전일 대비 색과 %, 매수·매도 구분과 매도 이유, 손익의 금액·비율을 표시합니다.
- **구현:** 메인에는 카드와 요약, 상세 화면에는 판단 근거와 진단 정보를 둡니다. 매매 기록은 메인에서 15개씩 최대 5페이지로 확인하도록 구성했습니다.
- **확인 기준:** “버튼이 눌린다”뿐 아니라 실제 화면 이동, 과거 자료 표시, 최신 시각과 모의 장부 기준을 함께 확인합니다.

### 5. 시장 차트는 하루의 흐름을 보여 주기

- **직접 제안:** SPY·QQQ·SOXX를 참고용으로 두고, 실시간 가격과 차트 기록 간격을 분리합니다. 최근 한 시간 대신 개장부터 폐장까지 1분마다 한 점을 남깁니다.
- **구현:** 가격은 수신할 때 갱신하고 차트는 1분 간격으로 보존합니다. 전일 종가보다 높으면 빨강, 낮으면 파랑으로 표시합니다. 큰 갭하락 때 선이 바닥에 눌리지 않도록 세로축은 수신 가격 범위에 맞춥니다.
- **남은 제약:** 수집하지 않은 시간은 복원하지 않습니다. 종가가 확인되지 않으면 마지막 장중 가격과 구분합니다. SOXX는 필라델피아 반도체지수 자체가 아니라 별도 반도체 ETF입니다.

### 6. AI 사용 횟수보다 설명이 필요한 시간을 기준으로

- **문제 제기:** “장 시작한 지 얼마 안 됐는데 AI 한도로 뉴스가 안 보이면 의미가 없다. 브리핑은 한 시간마다 호출하면 어떨까?”
- **구현:** 뉴스 분석과 브리핑의 호출 관리를 분리했습니다. 브리핑은 정규장 중 새 자료가 있을 때 최소 한 시간 간격으로 요청하고, 이전 설명과 작성 시각을 유지합니다. 월 비용 한도는 유지합니다.
- **함께 개선한 표현:** 내부 변수명 대신 쉬운 한국어를 쓰고, 시장·전략·매매 설명을 구분합니다.
- **역할 구분:** 뉴스 분석은 후보 순위의 보조 가점이고, 브리핑은 설명입니다. LLM이 직접 주문을 내리지는 않습니다.

### 7. 불필요한 기록을 줄이되 매매 근거는 보존

- **문제 제기:** “당일 거래에 필요 없는 자료는 정리하되 매매 기록처럼 필요한 것은 오래 남겨야 한다.”
- **구현:** 새 백업 성공 후 오래된 보조 자료를 제한된 양씩 정리하고, 주문·체결·잔액·복구 자료와 분석용 과거 분봉은 해당 자동 삭제 대상에서 제외했습니다.
- **추가 제안:** “분봉 지연을 기록하면 DB 부담이 커지지 않을까?”
- **구현:** 지연 진단은 정상 수집 때 추가 DB 작업 없이, 문제가 있을 때만 5분에 최대 한 건을 남깁니다. 최대 96건·256KiB로 제한해 상세 원문을 계속 복제하지 않습니다.

### 8. 장이 닫혀도 결과를 확인할 수 있게

- **문제 제기:** “휴장이나 폐장 후에도 켜서 업데이트된 내용을 확인하고 싶다.”
- **직접 제안:** VM까지 무조건 끄는 방식 대신 매매 프로그램과 조회 화면을 구분하고, 장이 닫혔으면 매매 시작 시 안내합니다.
- **구현:** 장 마감 저장·백업·정리 후 조회용 대시보드로 전환하고 VM은 사용자가 종료할 때까지 유지합니다. 휴장일 전용 업데이트 경로도 둡니다.
- **역할 구분:** 기획자가 PC를 꺼도 확인할 수 있는 접속을 요구했고, 구체적인 Tailscale 연결 방식은 Codex와 검토해 적용했습니다. Cloud Shell 세션·할당량이나 PC의 SSH 터널에 의존하지 않는 경로입니다.

## 운영 장애에서 배운 점

| 관찰한 문제 | 확인·대응 | 지금도 구분할 것 |
| --- | --- | --- |
| DB가 커지고 백업이 오래 걸림 | 시기별로 변경 로그와 상세 재현 기록의 증가를 확인. 보관 정책·백업 제한·서버 용량을 조정 | 삭제한 행 수와 디스크 파일 크기는 같지 않음. 다음 백업 시간도 확인해야 함 |
| 정리 중 DB 조회 시간 초과 | 조회 범위를 나누고 DB 메모리·단계별 시간을 확인 | 일부 구간의 빠른 조회만으로 전체 문제가 사라졌다고 할 수 없음 |
| 휴대폰 화면 연결 끊김 | VM·앱 상태와 Cloud Shell/SSH 연결 상태를 따로 확인 | 화면 연결 종료가 매매 엔진 종료를 뜻하지 않음 |
| 최신 분봉이 늦음 | 최신 봉이 없는 정상 응답의 제한 재확인과 지연 진단 기록 추가 | API 게시 지연, 누락, DB 처리 지연을 실제 운영 자료로 구분해야 함 |

이 장애들의 세부 SQL 수정, 메모리 값 선정, 재시도 구현은 Codex의 분석·구현 도움을 받아 진행했습니다. 기획자가 직접 한 일은 문제를 관찰하고, 무엇을 우선 고칠지 정하고, 실행 결과를 다시 확인하는 과정입니다.

## 결과와 아직 확인할 부분

실제 시세를 받아 모의 매수·매도·기록을 이어 보는 단계까지 진행했습니다. 자동 검사와 실제 장중 확인은 서로 다른 근거로 남깁니다. **단기 모의 체결이나 테스트 통과를 수익성·장기 운영 안정성의 증거로 설명하지 않습니다.**

다음 운영에서는 분봉 지연 기록, DB 용량 변화, 백업 시간, 매매 사유를 함께 확인합니다. 현재 매매 기준은 [매매 과정](TRADING_PROCESS.md), 운영 절차는 [GCP 안내](GCP_PAPER.md), 과거 설계 원문은 [이전 버전 문서](archive/README.md)에 있습니다.
