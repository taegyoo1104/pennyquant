# SessionQuant 실행과 구조

## 실행 환경

새 엔진은 `PAPER_LOCAL`에서 실행합니다. `LIVE_LOCAL`, `LIVE_GCP`는 데이터와 설정을 분리하기 위한 환경 이름이며 Phase 0~4 코드에서 실거래를 활성화하는 기능이 아닙니다. 기존 실거래 어댑터 소스는 보존하되 새 엔진은 Paper Broker만 사용합니다.

Python 3.12 이상과 프로젝트 의존성을 설치한 뒤 `python -m sessionquant doctor`로 확인합니다. 로컬 MySQL 8 서버와 전용 계정을 준비하는 절차는 [MYSQL_LOCAL.md](../reference/MYSQL_LOCAL.md)에 있습니다. `SQ_` DB 변수는 신규 이름이며 기존 `PQ_` 설정과의 호환 규칙은 DB 문서를 따릅니다.

`run`은 설정 파일, `replay`와 `backtest`는 정규화한 입력 파일을 받습니다. 수신 시각을 기준으로 처리하고 필요한 과거 데이터가 확인된 시점 이후에만 사용합니다. 실제 수집 파일에 합성 데모의 거래 가능 플래그나 RVOL을 붙여 거래를 유도하면 안 됩니다.

## 구성 요소

| 위치 | 역할 |
|---|---|
| `sessionquant/market/` | 시점별 유니버스, 봉 집계, 시장 상태, 스캐너, 네 전략, 토스 관측 |
| `sessionquant/portfolio/` | Decimal 장부, 소수점 Paper Broker, 비중·위험 예산, 추가매수, 세션 청산 |
| `sessionquant/news/` | 기존 기업 뉴스 수집·규칙·LLM 분석 |
| `sessionquant/macro/` | 공식 경제·GDELT·FRED 자료, 거시 위험, 두 단계 LLM와 비용 관리 |
| `sessionquant/database/` | SQLite 호환, MySQL 영속화, 마이그레이션, 실행 임대·보관 관리 |
| `sessionquant/dashboard/session_app.py` | 한국어 읽기 전용 운영 화면 |
| `config/sessionquant.yaml` | 새 시스템의 실행·전략·비용·뉴스 설정 |
| `sessionquant/dashboard/app.py` | 과거 PennyQuant 기록을 위한 호환 화면 |

이전 엔진·모델·전략 파일은 과거 결과의 재현을 위해 보존합니다. 새 실행 경로와 이전 재생 경로의 차이를 명시적으로 유지하며 기존 주문 ID를 새 이름으로 다시 만들지 않습니다.

## 모의주문의 의미

소수점 Paper Broker는 금액 매수와 수량 매도를 공통 주문 의도로 처리합니다. 금융 금액·수량은 Decimal이고, 직렬화할 때 정밀도를 잃지 않는 문자열로 보존합니다. 보유 비중은 계좌 평가금액을 기준으로 계산하며 예약 현금과 미체결 매수도 노출 한도에 포함합니다.

모의 체결은 이후에 들어온 유효 호가와 수량 제한을 사용합니다. 실제 증권사의 소수점 매칭 방식, 대기순서, 거래시간, 최소 주문 금액을 재현했다고 주장하지 않습니다. 체결이 확인되지 않은 주문은 포지션 청산 성공으로 기록하지 않습니다.

손절과 청산에는 최신 호가가 필요합니다. 거래정지·호가 지연·장 종료 때문에 청산되지 않을 수 있으며, 잔량과 실패 사유를 저장합니다. 일일 손실 한도에 도달하면 신규 진입을 막고 기존 포지션의 청산 관리를 계속합니다.

## 데이터 확인과 무거래 상태

`UNKNOWN`은 정상적인 상태 코드입니다. 대표적인 원인은 다음과 같습니다.

- SPY·QQQ의 최신 확정봉 또는 호가가 부족함.
- 5분봉·15분봉을 만들기 위한 1분봉이 누락되었거나 아직 끝나지 않음.
- 해당 날짜에 알려진 S&P 500 편입 기록이 없음.
- 계좌 거래 가능 상태·소수점 지원·거래정지·기업행동을 확인하지 못함.
- 비교 가능한 과거 자료가 없어 RVOL을 계산하지 못함.
- 뉴스 원문·공개 시각·공식 출처가 부족하거나 분석 요청이 실패함.

거래량이 많거나 가격이 올랐다는 이유만으로 누락 정보를 채우지 않습니다. 개별 기업의 긍정 뉴스는 필수가 아니지만, 시장·종목·위험 요건은 충족해야 합니다.

## 뉴스와 비용

기업 뉴스와 거시 뉴스는 별도 영역에 저장합니다. 제목·URL·내용 해시로 동일 기사의 재분석을 줄이고, 사건을 확정할 때는 공식 출처와 근거 문장을 확인합니다. GDELT의 발견 시각은 원문 발표 시각과 다를 수 있으며, 서로 다른 사이트에 실린 동일 배포 기사는 독립 확인 건수로 세지 않습니다.

LLM은 사실 추출과 위험 평가 결과를 반환할 뿐 주문 함수를 호출하지 않습니다. 신뢰도 값은 수익 확률이 아닙니다. 부정문·과거 사건·계획·루머·규칙 충돌은 확정 사실과 구분합니다. 뉴스 작업이 느리거나 실패해도 시세 처리와 세션 청산은 별도로 실행합니다.

모델 후보·단가는 설정값입니다. 접근 가능한 모델과 실제 API 요금은 사용자가 공식 문서 및 계정에서 확인해야 합니다. 토큰·캐시·예산을 저장하고 예산을 넘는 비필수 분석을 차단합니다. 대시보드의 최근 사용량 합계와 전체 월간 예산 원장을 구분합니다.

## 대시보드

```powershell
.\venv\Scripts\python.exe -m sessionquant dashboard --backend mysql --db data/sessionquant-paper-local.db
```

화면은 다섯 영역입니다.

1. 시장 현황: SPY·QQQ와 보조 ETF, 시장 상태, 경제 일정 확인 상태.
2. 종목 현황: S&P 500 후보 점수, 전략, 진입 근거와 차단 사유.
3. 포트폴리오: 현금·평가금액·소수점 수량·비중·추가매수·손절·손익.
4. 뉴스 분석: 기업/거시 기사, 공개/수집 시각, 판단 근거, LLM 사용량.
5. 주문 및 운영: 주문 상태, 모의 체결, 세션 청산 예정, 잔량·위험 경고.

시각은 KST로 표시하되 거래 세션은 뉴욕시간으로 판단합니다. DB의 최근 기록만 제한적으로 읽으며 과거 전체 시세를 한 번에 브라우저로 전송하지 않습니다. API 키와 DB 비밀번호는 표시하지 않습니다. 실거래 권한 자체는 화면에서 활성화하지 않습니다. 연결된 엔진에 시작·종목 매도·전체 종료 요청을 전달하고 엔진이 주문을 처리합니다.

## 종료와 복구

`Ctrl+C`는 엔진의 실행을 종료합니다. 종료 전에 이미 보유 중인 포지션이 있으면 장부는 보존되며, 프로그램 종료만으로 자동 청산 성공을 기록하지 않습니다. 재시작은 같은 실행 환경·DB·설정을 사용해야 합니다. 다른 계좌나 다른 전략의 장부에 이어 쓰지 마세요.

MySQL 쓰기가 실패한 경우 신규 주문을 계속 실행하지 않습니다. 같은 저장소의 실행 임대를 이용하여 중복 엔진을 막습니다. 이는 Phase 5~6에서 요구하는 실계좌 단위의 로컬/GCP 전역 중복 주문 검증을 대체하지 않습니다.

## 검증의 범위

합성 데모와 자동화 테스트는 규칙·복구·일관성의 검증 자료입니다. 실제 시세의 품질·전략 수익성·증권사 계정 권한·실제 소수점 체결·Windows 실행·GCP 운영 검증과 구분합니다. 사용자 PC의 MySQL 접속은 이 개발 환경에서 대신 완료할 수 없으므로 로컬 `db-check` 결과로 확인합니다.
