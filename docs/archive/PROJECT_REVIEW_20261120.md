## 다음 개선 우선순위

### 1. 실제 실행 시간과 주문 직전 확인

실행기는 한 처리 묶음의 시작 시각을 매매 엔진에 전달합니다. 엔진은 그 시각으로 호가 나이와 매매 시간을 검사합니다. 같은 묶음 안에서 DB 저장·계산이 오래 걸리면 실제 벽시계는 더 진행됐지만 판단 시각은 그대로일 수 있습니다.

실제 실행에서만 주문 직전의 시계를 추가로 확인하는 것이 다음 우선순위입니다. 단순히 모든 곳의 시각을 현재 시각으로 바꾸면 과거 입력 재생 결과가 달라질 수 있으므로, 추가 검사 결과를 기록하고 재생에서도 같은 결과를 사용해야 합니다. 이번 점검에서 신선도 허용 시간을 늘리지는 않았습니다.

### 2. 화면은 복구 장부 전체 대신 필요한 요약만 읽기

메인 화면은 약 5초마다 엔진 복구 상태를 읽습니다. 이 상태에는 누적 주문·체결·알림도 포함돼 있어 운영 기간에 따라 읽는 양이 늘어날 수 있습니다. 계좌 요약과 현재 보유·최근 체결만 읽는 화면용 자료로 분리하는 것이 좋습니다.

AI 비용 화면도 사용자가 잔액 확인 기록을 입력한 경우 전체 사용 이력을 훑어 이후 비용을 계산합니다. 기록을 나눠 읽어 메모리는 제한하지만 전체 DB 처리량은 줄이지 못합니다. 날짜 범위를 이용한 조회·집계를 추가하되, 미확정 비용과 확인 시각을 걸친 요청의 불확실성은 유지해야 합니다.

이 둘은 코드에서 확인한 증가 요인입니다. 현재 사용자의 화면 지연에서 각각 차지하는 시간은 운영 측정이 필요합니다.

### 3. 자료 정리의 처리량과 잔여량 측정

현재 종료 시 자료 정리는 시간과 행 수에 상한이 있습니다. 안전하게 짧게 끝나는 장점이 있지만, 10종목을 2초마다 모두 기록하면 6.5시간 동안 호가만 최대 약 117,000행이 생길 수 있습니다. 실제 수신량은 이보다 적을 수 있으며, 현재 한 번의 정리는 전체 대상에서 최대 50,000행을 검사합니다.

일별 생성량, 삭제량, 가장 오래된 정리 대상의 날짜를 먼저 측정해 정리가 유입량을 따라가는지 확인해야 합니다. 백업 크기만으로 실패 여부나 삭제 효과를 판단하지 않습니다. 회계 장부·재생 근거를 임의로 지우는 변경은 하지 않습니다.

### 4. MySQL 변경에 대한 자동 검사 범위

일반 PR CI는 오프라인·SQLite 검사이고 실제 MySQL 검사는 수동 실행입니다. DB·저장 정책을 바꾸는 PR에는 폐기 가능한 MySQL 통합 검사를 자동으로 붙이는 방식을 권합니다. 운영 DB를 검사에 사용하지 않습니다.

### 5. 기존 엄격한 모의 프로필의 미체결 주문 재검사

현재 권장 모의 정책은 체결 때 상장 자료와 웹소켓 사용 가능 여부를 다시 확인합니다. 별도의 기존 엄격한 정책에서는 매수 주문 뒤 종목 적격성이 제한 상태로 바뀌어도 이미 대기 중인 주문의 체결 경로에 그 제한이 모두 전달되지 않는 경우를 재현했습니다. 해당 프로필을 다시 사용할 때는 미체결 매수의 취소·체결 직전 적격성 검사를 보강해야 합니다. 이번 수정이 기존 프로필의 모든 적격성 검사를 해결했다는 뜻은 아닙니다.
