# 설치·배포·운영 매뉴얼

## 설치

Python 3.12 이상으로 Windows, Linux, macOS에서 실행합니다. Windows는 일반 Windows용 Python을 사용할 수 있으며 WSL2도 선택할 수 있습니다. 프로젝트 루트에서 가상환경을 만들고 README의 운영체제별 잠금 파일 설치 순서를 실행하세요. Windows·PyCharm의 자세한 설정은 [Windows 실행 안내](WINDOWS_PYCHARM.md)에 있습니다. 실제 Windows OS 실행 검증은 아직 수행하지 않았으며, 검증한 환경과 검사 결과는 `VALIDATION.md`에 기록합니다.

Windows PowerShell에서는 `.\.venv\Scripts\python.exe`를 직접 실행하면 가상환경 활성화나 실행 정책 변경 없이 설치·데모·대시보드를 실행할 수 있습니다. Linux/macOS 또는 WSL에서는 `source .venv/bin/activate` 후 `python`을 사용합니다. 이 문서의 `python` 명령은 해당 가상환경의 Python을 뜻합니다.

프로그램과 대시보드는 로컬 PC에서 동작하므로 별도 클라우드 서버가 필요하지 않습니다. 데모는 API 키 없이 실행할 수 있고 실제 데이터 수집에는 제공자 계정·인터넷 연결이 필요합니다. 최소 메모리는 보장값을 정하지 않았으며 소형 VM 사용 전 실제 관심 종목 수로 부하를 측정하세요. SQLite 파일과 WAL은 로컬 디스크에 둡니다.

`doctor`는 설치 버전과 paper 모드만 출력하며 인터넷 연결이나 계정 권한을 검사하지 않습니다. `.env.example`은 변수 이름 안내용입니다. 셸·환경 관리자의 안전한 입력 기능으로 실제 값을 주입하세요. 토스 계정 관련 조회에는 `TOSS_ACCOUNT_SEQ`도 필요합니다.

## 데모와 보고서

`python -m pennyquant demo --out data`로 합성 테이프, 모의주문 DB, JSON/Markdown 보고서를 만듭니다. 보고서는 10개 뉴욕 세션의 앞 6개와 뒤 4개를 분리하고 각 구간의 시작 자본을 독립적으로 설정합니다. 동일 이벤트와 비용을 사용하며 파라미터를 학습하거나 최적 전략을 선정하지 않습니다.

실제 관측 보고서는 신뢰할 수 있는 정규화 입력으로 `backtest`를 실행해 만듭니다. 수신 이력이 없는 과거 뉴스에 과거 수신 시각을 만들어 넣지 마세요. 가격 조정·상장폐지 포함·뉴스 라이선스·실시간 권한은 데이터 공급 단계에서 검증해야 합니다. 수수료는 예시 bp 모델이고 실제 최소 수수료·규제 수수료·환전 비용을 재현하지 않습니다.

PF는 완료 거래의 순이익 합/순손실 절댓값 합입니다. 손실 거래가 없으면 JSON null과 ‘계산 불가’로 표시합니다. 순손익과 최종 자산은 마지막 유효 매수호가로 평가한 보유분도 포함합니다. 기말 청산 호가를 만들지 않으므로 미청산 포지션과 완료 거래 손익을 함께 확인하세요.

## 실시간 모의매매 운영

1. 제공자별 키·실시간 뉴스 권한·시세 사용 조건을 확인합니다.
2. 단일 생산자가 완료된 1분봉, 호가, 검증한 거래 가능 상태·누적지표를 포함한 snapshot, 뉴스를 수신 순서대로 JSONL에 기록합니다. RVOL은 비교 가능한 과거 동일 시간대 관측이 충분할 때만 입력합니다.
3. 새 DB로 `python -m pennyquant paper --input data/live-events.jsonl --db data/live-paper.db`를 실행합니다.
4. 별도 프로세스로 대시보드를 해당 DB에 연결합니다. 수집기 예외·시세 지연·주문 이상을 관찰합니다.
5. 종료는 Ctrl+C로 합니다. DB의 주문·포지션은 다음 실행을 위해 남습니다. 프로그램 종료 자체는 포지션 청산 요청이 아닙니다.

기본 `collect toss`는 호가를 수집하지만 상장 상태를 현재 주문 가능성으로 간주하지 않습니다. 제공자가 직접 주지 않는 RVOL·정지 여부를 채우는 자동 완성 파이프라인은 포함하지 않습니다. `paper`는 외부의 완전한 정규화 생산자와 연결하는 실행 경로입니다. 수집 파일 병합은 수신 시각 순서와 중복 처리 원칙을 지켜야 합니다.

실시간 엔진은 이벤트의 수신 시각과 별도로 현재 UTC 시각을 위험 검사에 사용합니다. 예전 입력 대기열을 처리해도 오래된 호가로 모의체결하지 않습니다. 기록 재생인 `replay`에서는 기록된 수신 시각을 시뮬레이션 시계로 사용합니다.

## 중지·복구

버전 업데이트 전에는 실행 중인 엔진·수집기를 모두 종료한 뒤 최신 의존성을 설치하고 재시작하세요. 수집기는 데이터 파일 옆의 `.writer.lock`, 엔진은 DB 옆의 `.engine.lock`으로 중복 실행을 막습니다. 이전 버전의 수집기는 데이터 파일 자체를 잠갔으므로 서로 다른 버전을 동시에 실행하지 않습니다. 잠금은 데이터 파일과 분리되어 있어 Windows에서도 수집 중 파일 소비자가 읽을 수 있습니다.

대시보드 ‘신규 진입 중지’는 DB `manual_halt`를 켭니다. 엔진은 이벤트 처리와 유휴 확인에서 이를 적용하고 기존 신규 매수의 미체결 잔량도 취소합니다. 보유 수량의 손절·익절 관리는 계속합니다. 재개는 사용자 중지만 해제하며 일일 손실·연속 손실·미확인 주문·잔고 불일치는 별도로 남습니다.

클라이언트 주문 ID는 신호에서 결정되며 재호출은 기존 주문을 반환합니다. 같은 ID의 내용이 바뀌면 신규 진입을 차단합니다. `unknown` 상태는 재주문하지 않으며 `reconcile()`이 외부 상태와 주문·포지션이 일치하는지 확인합니다. 새 통합 실행의 실제 계좌 대사·주문 전송은 [SYSTEM_RUN.md](SYSTEM_RUN.md)의 별도 조건을 따릅니다. 기존 replay·paper·run-toss 명령은 실제 주문을 보내지 않습니다.

재시작 시 설정·전략이 같아야 하고 DB별로 한 엔진만 쓸 수 있습니다. 기록 재생은 전체 입력 SHA-256과 커서, 실시간 파일 소비는 오프셋과 소비한 앞부분 해시를 상태와 같은 SQLite 트랜잭션에 저장합니다. 변경된 파일·섞인 런타임 모드·변경 설정은 새 DB를 사용하세요. 디스크 장애나 저장 오류가 발생하면 프로세스를 중지하고 DB를 점검한 뒤 재개합니다.

수수료·부분 체결·현금·예약금·보유 수량·미체결 주문은 상태에 포함됩니다. 손절·익절 주문은 실제 체결 수량에 대해서만 생성하고 다음 유효 호가에서만 체결될 수 있습니다. 급락 시 지정가를 밑돌면 미체결이 유지되며 TTL 이후 다음 호가에서 재평가합니다. 이는 거래소 OCO가 아닙니다.

## 데이터 보관

DB와 `-wal`·`-shm`은 실행 중에 임의로 복사하지 마세요. SQLite 백업 API를 쓰거나 엔진과 대시보드를 종료한 뒤 파일을 보관합니다. 모든 이벤트·호가·로그를 무기한 저장하면 DB가 커지므로 초기에는 관심 종목만 수집하고 보관 기간을 정하세요. 계정 데이터가 있는 DB·로그는 개인 자료로 관리합니다.

## Docker

Dockerfile은 배포 예시이며 이번 환경에서 이미지 빌드·VM 운영은 검증하지 않았습니다. README 순서로 먼저 `data/` 데모를 만든 뒤 실행할 수 있습니다.

```bash
docker build -t pennyquant:0.1.0 .
docker run --rm --name pennyquant-dashboard -p 127.0.0.1:8501:8501 -v "$PWD/data:/app/data" pennyquant:0.1.0
```

이미지는 UID 1000의 일반 사용자로 실행합니다. 호스트 디렉터리 권한을 맞추고, 여러 컨테이너가 같은 DB를 갱신하지 않도록 하세요. VM에서는 기본 Streamlit 포트를 인터넷에 직접 노출하지 말고 SSH 포워딩 등 본인 전용 접근을 구성합니다. 고정 IP·브로커 허용 IP·시간 동기화·재부팅 후 프로세스 실행·디스크 알림은 실제 운영 환경에서 별도로 확인합니다.

## 실거래 이행 전 남은 일

실제 계정의 인증·호가·주문 가능 종목·미체결·취소·부분 체결·타임아웃과 실제 비용을 확인해야 합니다. 시장 데이터 생산자를 검증하고 충분한 전향적 모의매매 기록으로 위험·중복·복구 조건을 확인한 뒤 실제 주문을 사용합니다. 공통 전략 설정은 `mode: paper`를 유지하며, 실제 주문 선택은 통합 실행의 pipeline 모드와 `--live --acknowledge-live-orders`로 분리되어 있습니다. 기존 토스 시세 어댑터의 `create_order()`는 차단된 상태이고 별도 TossBroker가 주문을 담당합니다. 서버 보관 OCO·장기간 실계좌 운용은 검증하지 않았습니다.
