# 호가 웹소켓 전환 — 단계별 범위

## 1단계: 독립 수신 기반 (구현)

`collectors/toss_quote_feed.py`의 `TossQuoteFeed`는 최대 50개 후보와 후보 밖 보유·미체결 종목을 합쳐 **호가만** 구독한다. 중복을 제거하며 총 100개를 초과하면 오류로 알린다. 보유 종목을 조용히 잘라내지 않는다. 체결 스트림, 실계좌 주문 이벤트, 거래량·분봉 재구성은 포함하지 않는다.

메모리에는 종목당 최신 호가 하나만 보관한다. 수신 메시지마다 DB를 쓰거나 전략을 계산하지 않으며, 매매 엔진·DB·주문 API를 호출하지 않는다. 원본 호가 시각과 수신 시각은 구분한다. `latest()`는 구독 수락·연결 상태와 두 시각의 신선도를 검사하고, 사용할 수 없으면 `None`을 반환한다. 독립 점검 기본값은 30초이고, 운영 연결은 엔진·체결 모형 중 더 짧은 제한(현재 기본 10초)을 적용한다. 연결의 `pong`을 시세 신선도의 증거로 사용하지 않는다.

- 구독 ack 이후 초기 REST 호가를 별도 비동기 작업에서 조회한다. 보유·미체결을 먼저 조회하며, 동일 REST 클라이언트의 요청 제한을 공유하는 단일 작업으로 처리한다. 이미 신선한 웹소켓 값이 있으면 초기 조회를 건너뛴다. 50개 초기 조회는 즉시 완료된다고 보장하지 않는다.
- 초기 REST가 느려도 웹소켓 수신은 계속한다. REST가 실패한 종목은 실패 수를 표시하고 다음 웹소켓 갱신을 기다린다. 늦게 도착한 오래된 REST 결과가 최신 웹소켓 값을 덮어쓰지 않는다.
- 연결 종료·구독 변경 즉시 이전 시세를 무효화한다. 재연결 후 새 ack와 새 자료가 필요하다. 초기 조회나 이전 연결에서 늦게 돌아온 결과는 연결 세대 번호로 거부한다.
- 재시도는 기본 1, 2, 4, 8, 16, 30초로 늘어나며 최대 30초다. 60초 이상 유지된 연결 뒤에는 재시도 단계를 초기화한다. ack는 15초, 연결 전체 무수신은 90초 제한이다. 구독 일부 거절 시 전체 연결을 사용 불가로 처리하고 오류 유형을 표시한다.
- 이번 단계의 구독 변경은 **기존 연결을 닫은 뒤 새 전체 목록으로 재연결**한다. 연결을 겹쳐 열지 않지만 잠깐 수신 공백은 생긴다. 같은 종목 집합을 반복 전달하면 재연결하지 않는다. 보유·미체결 목록은 호출자가 전달해야 하며 자동 DB 조회는 하지 않는다.
- 같은 시각의 동일 호가는 중복으로 버린다. 같은 시각인데 내용이 충돌하면 해당 종목 값을 무효화하고 더 새로운 시각의 자료를 기다린다. 끊긴 동안의 모든 호가 변경을 복구하거나 유실이 전혀 없다고 보장하지 않는다.

`snapshot()`은 구독 수·신선한 종목 수·수신/실패 횟수·재시도 간격·오류 유형을 반환한다. `SUBSCRIBED`는 구독 수락이며 매매 준비 완료가 아니다. 종목별 자료는 별도로 확인한다. 원시 인증 오류·토큰·응답 전문은 출력하지 않는다.

### 별도 수신 점검

```bash
python -m sessionquant.ws_probe --symbols AAPL MSFT --seconds 60
```

이 명령만 명시적으로 실행하면 실제 토스 시세 연결을 열고 5초마다 상태 JSON을 출력한다. 주문·LLM·DB 연결은 없다. `.env` 또는 환경변수의 기존 토스 설정을 읽는다. 시세 수신이 없는 시간에도 정해진 기간 동안 상태를 관찰하므로 명령 종료만으로 연결 성공을 판단하지 말고 `acknowledged`와 `fresh_count`, 오류 유형을 확인한다. 종료하면 연결과 초기 REST 작업을 정리한다.

**동일 토스 인증의 기존 엔진·별도 수집 프로세스를 중지한 상태에서 점검한다.** 새 프로세스의 토큰 발급이 기존 연결에 영향을 줄 수 있으며 계정당 웹소켓 연결 한도는 2개다. 운영 연결은 하나의 REST 인증 클라이언트를 공유한다. 이번 구현 검증은 가짜 공급자·전송 계층으로 수행했으며 실제 토스 계정이나 GCP에는 접속하지 않았다.

## 2단계: 모의매매 엔진 연결 (구현)

**이 단계까지 적용하면 제한적인 Paper 테스트 운영이 가능하다.** 실제 토스/GCP 수신·처리 속도는 배포 후 확인해야 하며, 수신 성공이 매매 조건 충족을 뜻하지는 않는다. 기존 화면은 유지한다.

- `quote_transport: websocket`을 명시한 별도 프로필만 사용한다. 토스·단순 눌림목·observed Paper·후보 50개 이하로 범위를 제한했다. 후보 50개와 후보 밖 보유·미체결·청산 대기 종목을 자동 구독한다.
- 수신은 분봉 HTTP 조회와 별도 비동기 작업이다. **집중 10개와 위험 관리 종목의 최신값만 약 2초마다 한 묶음으로** 엔진에 전달한다. 수신 패킷마다 DB 저장·전략 평가를 하지 않는다. 엔진/DB 처리가 오래 걸리면 전달 주기도 늘어나므로 2초 지연을 보장하지 않는다.
- 분봉·거래대금·상장 정보는 REST를 유지한다. 후보별 반복 REST 호가 조회와 그 예약 시간을 없애고 분봉 조회에 사용한다. 초기 호가 조회는 같은 인증·요청 제한을 공유한다. 웹소켓으로 분봉이나 RVOL 거래량을 재구성하지 않는다.
- 연결 단절·미수신·오래된 호가는 `websocket_quote_unavailable`로 신규 진입을 막고, 엔진의 다음 처리에서 남은 매수 주문도 취소한다. 보유·미체결·청산 대기 종목에 신선한 호가가 없으면 기존 REST 요청 예산 안에서 대체 조회한다. **매도는 이 진입 차단과 무관하게 계속 관리**하지만 REST까지 실패하거나 오래되면 체결을 만들어 내지 않는다.
- 재연결은 새 구독 수락과 자료가 필요하다. 같은 시각의 호가를 다시 받아도 새 유동성으로 체결하지 않는다. 원본 시세·수신 시각과 실제 엔진 전달 시각(`delivered_at`)을 구분해 저장한다. 재생에도 단절 당시 진입 차단 상태를 기록한다.
- 새 프로필의 `quote_alignment_seconds: null`은 **종목 간 2초 비교만** 없앤다. 개별 호가의 원본 시각·수신 시각, 스프레드·잔량·상장 상태·확정봉·매매 시간·위험 한도 검사는 유지한다. 기존 프로필의 2초 설정은 유지한다.
- 단순 눌림목은 RVOL을 필수 매수 조건으로 쓰지 않는다. 당일 5분봉·15분봉과 ATR 준비, 개장 후 75분 진입 기준은 그대로다. 웹소켓 연결만으로 무조건 매수하거나 분봉 부족을 해결하지 않는다.

### 로컬 실행

기존 엔진을 종료하고, 기존 장부의 보유·미체결이 없는지 확인한다. 웹소켓 테스트는 별도 장부로 시작한다. MySQL에서 `.env`의 `SQ_DB_NAMESPACE`가 지정돼 있으면 파일 경로보다 우선하므로 **새 namespace**로 실행한다.

```bash
# Bash: 한 실행에만 적용. 기존 데이터는 삭제하지 않는다.
SQ_DB_NAMESPACE=sessionquant-strategy-lab-ws-v1 \
  python -m sessionquant run --config config/sessionquant.strategy-lab-websocket.example.yaml
```

PowerShell에서는 먼저 `$env:SQ_DB_NAMESPACE="sessionquant-strategy-lab-ws-v1"`을 지정한 뒤 같은 `python -m sessionquant run ...` 명령을 실행한다. 새 장부의 감시목록·당일 분봉 준비가 다시 필요할 수 있다. 시작 버튼을 누르기 전 연결 상태와 현재 집중 종목의 자료를 확인한다.

### GCP 선택 방법

코드를 병합·이미지 업데이트한 뒤 **운영 VM `sessionquant-paper`에서** 설정한다. 기존 장부가 보유·미체결 없이 종료됐고 새 백업이 성공한 상태에서 프로필을 바꾼다. 기존 설정·장부를 덮어쓰거나 DB를 초기화하지 않는다.

1. `sessionquant.service`를 중지하고 기존 절차로 DB를 켜서 `backup.sh`의 `UPLOADED`를 확인한다.
2. `/etc/sessionquant/app.env`에 아래 두 항목을 지정한다. 다른 인증·DB 연결값은 유지하고 파일 내용을 채팅에 붙이지 않는다.

   ```dotenv
   SQ_SESSION_CONFIG=config/sessionquant.strategy-lab-websocket.example.yaml
   SQ_DB_NAMESPACE=sessionquant-strategy-lab-ws-v1
   ```

3. 장전 운영 가능한 시간에 `sudo systemctl start sessionquant.service`로 시작한다. 대시보드가 준비된 뒤 기존 SSH 터널로 접속한다. GCP 기본 Compose는 이 환경변수를 컨테이너 안에서 읽으며, 미지정 시 기존 REST 설정을 사용한다. 업데이트 전 장부 점검과 장 마감 자료 정리도 선택한 설정을 따른다. VM 자동 종료·백업 절차는 유지한다.

테스트 종료 뒤 기존 프로필로 돌아갈 때에도 먼저 새 장부가 보유·미체결 없이 종료됐는지 확인하고 백업한다. `SQ_SESSION_CONFIG`와 `SQ_DB_NAMESPACE`를 **함께** 기존 값으로 복원한다. 한쪽만 바꾸면 다른 장부를 보거나 실행 정책 불일치로 중단될 수 있다.

### 실행 중 점검

`websocket_quotes_v1` 제어 기록은 약 10초마다 연결·구독 수·신선한 호가 수·전달 묶음 수·마지막 호가 묶음의 엔진 처리 시간을 저장한다. 현재 화면에서 보이지 않더라도 다음 **읽기 전용 명령**으로 확인할 수 있다. 운영 VM 터미널에서 실행하며, 실행 중인 엔진을 재시작하거나 별도 토스 토큰을 발급하지 않는다.

```bash
sudo docker compose -f /opt/sessionquant/deploy/gcp/compose.yaml exec -T app \
  python -m sessionquant paper-status --config config/sessionquant.strategy-lab-websocket.example.yaml
```

출력의 `quote_transport`가 `websocket`, `websocket.state`가 `SUBSCRIBED`, `acknowledged`가 true인지 확인한다. `engine.heartbeat_fresh`와 `websocket.observed_at`도 함께 확인한다. 오래된 저장 상태를 현재 연결 상태로 해석하지 않는다. `fresh_count`는 전체 구독 중 신선한 수이고 `selected_fresh_count`는 현재 집중·위험 관리 종목 중 신선한 수다. 집중 종목별 매수 가능 여부는 `latest_candidates`의 차단 사유에서 확인한다. `delivery_batches`가 증가하는지와 실제 모의 주문·체결·매도 기록을 확인한 뒤 테스트를 확대한다.

## 3단계: 화면과 GCP 검증 (미구현)

- 화면에 연결·구독·종목별 지연 상태를 표시하고 전체 화면 재실행 부담을 줄인다.
- GCP의 50종목 실제 수신량, CPU·메모리, 엔진 처리 시간과 DB 저장량을 측정한다.
- 필요할 때 서버 사양을 조정하고, 읽기 전용 점검 후 모의매매를 검증한다.

기본 `python -m sessionquant run`과 기존 설정은 REST 운영을 유지한다. 웹소켓 프로필은 명시적으로 선택해야 한다. 이 저장소의 자동 검증은 합성 입력·가짜 HTTP/웹소켓 및 로컬 루프백 연결을 사용하며 실제 토스 계정·GCP의 처리량 검증을 대신하지 않는다.
