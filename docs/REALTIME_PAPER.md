# 실제 시세·뉴스를 사용하는 Paper 운영

목표는 토스 시세와 실제 기업/거시 뉴스를 수집하고, OpenAI 분석을 기술 전략·후보 선정에 결합하되 매매는 가상 계좌에서만 실행하는 것이다. 로컬 MySQL부터 사용한다. KIS나 실거래 활성화는 포함하지 않는다.

## 1. 기존 분봉을 재사용해 준비

이미 다른 설정으로 과거 분봉을 수집해 둔 경우에만 사용하는 일회 복사 절차다. **처음 설치했다면 [시작 안내](GETTING_STARTED.md)를 따라 바로 실행해 자동으로 자료를 준비할 수 있다.** 기존 자료를 복사하려면 `run`, 분봉 수집, 토스 연결 검사 프로그램을 중지한 뒤 PyCharm 터미널에서 실행한다.

```powershell
git switch wip/stage06-handoff-20261115
git pull --ff-only origin wip/stage06-handoff-20261115
python -m sessionquant prepare-paper --source-config config/sessionquant.candidates.example.yaml --config config/sessionquant.realtime-paper.example.yaml
```

`PREPARED`이면 준비가 끝났다. 이 명령은 **처음 한 번만** 실행한다. 기존 DB의 과거 분봉과 시총 수집 자료를 새 `sessionquant-realtime-paper-v1` 실행 공간으로 복사한다. 최초 수신 시각을 유지하며, 기존 거래·포지션·엔진 상태·매매 시작 요청은 복사하지 않는다. 복사 실패는 대상 트랜잭션을 되돌린다. 이미 준비한 대상에는 덮어쓰지 않는다. 원본은 그대로 남는다.

원본과 대상 설정은 같은 `universe_path`를 사용해야 한다. `SQ_DB_NAMESPACE` 또는 `PQ_DB_NAMESPACE`로 두 설정을 같은 MySQL 공간에 강제한 경우 복사를 거부한다. 일반적인 기존 설정은 `db_path` 이름으로 공간을 구분하므로 추가 설정이 필요 없다. 사용자별 포트폴리오·뉴스 설정을 변경했다면 새 YAML에도 반영한다. 비밀키는 기존 환경변수/로컬 `.env`에서 읽는다.

```powershell
python -m sessionquant watchlist-refresh --config config/sessionquant.realtime-paper.example.yaml
python -m sessionquant watchlist-status --config config/sessionquant.realtime-paper.example.yaml
```

시총 수집이 `collecting`이면 표시된 재시도 시각 이후 다시 실행한다. 기본 50개 중 시총을 확인할 수 없는 기업은 제외하고, 직전 20개 정상 거래일 및 사이 조기 폐장일의 분봉이 준비된 종목만 일일 운영 대상으로 사용한다. 실제 개수는 날짜와 DB 검사 결과에 따라 달라진다. 빈자리를 다른 종목으로 채우지 않는다.

거래일이 바뀌면 비교 기간도 바뀌며 `run`의 자동 예열이 확인·보충한다. 별도로 장전에 미리 보충하려면 엔진을 중지한 상태에서 아래 명령을 **운영에 쓰는 같은 설정으로** 실행한다. 매일 수동 실행해야 하는 절차는 아니다. 완료한 거래일은 건너뛰며 준비된 종목이 없으면 신규 진입을 막는다.

```powershell
python -m sessionquant history-backfill --config config/sessionquant.realtime-paper.example.yaml
python -m sessionquant history-status --config config/sessionquant.realtime-paper.example.yaml --details --output history-before-open.json
```

`--output`은 새 파일에 저장한다. 같은 이름을 재사용하려면 다른 파일명을 지정한다. 전체 수집이 `INCOMPLETE`여도 일일 운영 목록에 준비된 종목이 있으면 그 종목들로 운영할 수 있다. 장중에는 가격·현재 분봉을 갱신하며 매번 전체 20거래일을 다시 받지 않는다.

## 2. 실제 뉴스와 LLM을 단독 진단

먼저 엔진을 중지한 상태에서 연결과 설정을 확인한다.

```powershell
python -m sessionquant check-news --config config/sessionquant.realtime-paper.example.yaml --connect --provider openai
python -m sessionquant paper-news-probe --config config/sessionquant.realtime-paper.example.yaml --symbol NVDA
```

첫 명령은 모델 접근만 검사한다. 두 번째 명령은 지정 기업의 실제 SEC/RSS/선택적 Alpaca 수집을 사용하고, 검증 가능한 최신 기사에 **실제 LLM 생성 요청을 실패 포함 최대 1회** 보낸다. 과금이 발생할 수 있으며 기존 월/일/시간 예산과 감사 원장을 함께 사용한다. 재시도·상위 모델 분석도 이 1회 제한을 넘지 못한다. 주문은 생성하지 않는다.

| 진단 상태 | 의미 |
| --- | --- |
| `VALID_RESPONSE_AND_STRATEGY_CONTEXT` | 유효한 분석이 기업 뉴스 가점/위험 조회에 연결됨. `analysis_ids`와 `llm_call_ids`로 추적 가능 |
| `VALID_RESPONSE_REVIEW_CONTEXT` | 응답은 유효하지만 뉴스 가점에 사용할 확정 근거가 부족하거나 아직 조회 가능한 시각이 아님 |
| `LLM_ATTEMPT_FAILED_OR_INVALID` | 요청은 했으나 HTTP/형식/내용 검증 등을 통과하지 못함. 오류와 호출 상태 확인 |
| `NO_ELIGIBLE_NEWS_OR_BUDGET_BLOCKED` | 최신 원문이 없거나 수집/예산/공급자 대기 조건으로 요청하지 못함. `issues`·`analysis_errors` 확인 |
| `NO_OPENAI_KEY` | 현재 프로세스에 OpenAI 키가 없음 |

기본 진단 기업은 공식 RSS가 등록된 NVDA다. AAPL 등 기본 RSS가 없는 기업은 SEC 등 다른 소스가 필요하다. 최근 24시간 기사·본문·출처/종목 연결이 없으면 오래된 기사나 제목만으로 생성을 강행하지 않는다. 주말에 분석 요청 0회가 나오는 것은 정상일 수 있다. `SEC_USER_AGENT`, OpenAI 등 설정은 [뉴스 설정](reference/NEWS_SETUP.md)을 따른다.

뉴스 진단 성공은 장중 거래 검증 성공과 다르다. 또한 뉴스 부재/LLM 오류가 차트 전략 전체를 중단시키지는 않는다. 미확인 뉴스 가점은 적용하지 않고, 이미 확인된 악재·경제 일정·손절·청산 규칙은 유지한다.

## 3. 장중 실행

### 실행 시 자동 예열

토스 감시목록을 사용하는 `run`은 장전·장중 어느 때에 시작해도 먼저 **자료 준비**를 수행한다. 이미 `prepare-paper`로 준비한 원장에 매일 복사를 반복하지 않는다. 이전 실행을 일찍 종료했더라도 다음 시작 때 누락된 과거 거래일을 보충한다.

1. 유효한 시총 후보를 확인한다. 자료 준비 전에는 운영 감시 목록을 확정하지 않는다.
2. 최근 20개 정상장과 사이의 조기 폐장일을 대상으로 저장 내용의 해시를 확인한다. **이전 검사에서 완전했고 내용이 그대로인 종목·날짜는 검사 결과를 재사용**한다. 끝까지 조회했지만 누락·충돌이 남은 구간도 내용이 그대로라면 마지막 검사 후 6시간 동안 재조회를 생략하고 해당 종목을 계속 제외한다. 나머지만 분봉을 읽어 검사하고 누락된 가장 최근 분을 조회 기준으로 삼아 필요한 페이지를 보충한다. 원본 수신 시각과 값 충돌은 보존한다.
3. 장중이면 현재 시점까지의 당일 분봉도 확인·보충한다. DB에 저장된 분봉은 API 재조회 없이 엔진에 전달하고 누락 구간만 조회한다. 원본 수신 시각과 이번 실행에서 복원한 시각은 별도로 기록한다. SPY·QQQ와 보유·주문 관련 종목을 포함하며 과거 검사 후 잡은 기준 시각이 화면에 표시된다.
4. 검사 종료 후 과거 자료가 준비된 종목으로 운영 목록을 확정한다. 종전 실행에서 같은 날 제외됐던 종목도 재시작 예열에서 자료가 복구되면 새 관측 시각으로 다시 선정할 수 있다. 이후 그 실행 중에는 목록을 고정한다. 당시 선택 이력은 연구 기록에 보존한다.

예열 중에는 **매매 시작**을 사용할 수 없고 엔진도 시작 요청과 새 매수를 막는다. 기존 미체결 매수 취소, 보유 종목 시세·손절·청산은 계속 처리한다. API 읽기는 기존 회차별 호출·시간 제한과 429 대기를 공유하며 보유 위험 조회 다음에 진행한다. 뉴스 수집은 기존 독립 주기로 계속된다. 새 유료 LLM 재시도나 실주문 기능은 추가하지 않는다.

예열은 고정된 5분/10분 타이머가 아니다. 이미 저장된 자료량·누락 날짜·API 응답과 제한에 따라 달라진다. 첫 수집이나 누락이 많으면 오래 걸릴 수 있다. 중단하더라도 저장된 분봉은 남으며 다음 실행에서 완전성을 다시 검사한다. API가 제공하지 않는 누락/충돌은 보간하지 않고 상세에 남긴다.

재시작 예열의 중복 조회는 줄였지만 시총 후보 갱신, 처음 받는 과거 자료, DB 검사, 최신 호가 조회 시간은 필요하다. 호출 제한을 높이거나 최신 시세 검사를 생략해서 준비 완료로 표시하지 않는다. 실제 PC의 총 준비 시간은 단계별 진행 상황으로 확인한다.

**업데이트 후 첫 실행에는 누락 구간을 한 번 더 조회할 수 있다.** 이전 버전에 없던 재조회 대기 기록을 만들기 위해서다. 이미 저장된 완전한 구간의 검사 결과는 그대로 재사용한다. 예를 들어 1,000개 중 872개가 완전하고 나머지 128개를 끝까지 조회했지만 누락이 남았다면, 6시간 이내 재시작 때 두 그룹 모두 과거 재조회에서 빠질 수 있다. 화면에는 ‘완료된 과거 검사 재사용’과 ‘최근 조회한 누락 구간 재조회 생략’을 구분해 표시한다. 누락 종목을 정상으로 인정하는 것은 아니다.

대기 시간은 재시작으로 연장되지 않는다. 6시간이 지난 뒤의 예열, DB 자료 변경·삭제, 달력 경계나 검사 버전 변경 시 다시 확인한다. 새로 비교 대상에 들어온 거래일·종목과 당일 분봉 보충은 별도로 처리한다. API 오류·요청 제한으로 대기 중이거나 페이지 한도·조회 위치 오류 때문에 끝내지 못한 구간에는 6시간 생략을 적용하지 않는다. 대기 중에도 엔진을 중지하고 `history-backfill`을 실행하면 바로 보충을 시도할 수 있다. 이 수동 명령은 재조회 대기 기록을 사용하지 않는다.

검사 결과는 원본 전체 내용의 해시·거래일 개폐장 시각·검사 규칙 버전·검사 시각과 묶어 저장한다. DB 직접 수정/삭제, 달력 변경, 규칙 버전 변경, 과거 시각으로 재생하는 경우에는 재사용 조건을 다시 확인한다. 미래에 수신되는 수정본이 함께 저장돼 있으면 완료 검사 결과를 캐시하지 않는다. 마지막 감시 종목 선정에도 같은 검증 결과를 사용해 전체 분봉 계산을 반복하지 않는다. 해시는 DB에서 계산하므로 MySQL에서는 변경 없는 대용량 원문을 네트워크로 다시 받지 않는다. 별도 스키마 변경이나 SQL 실행은 필요 없다. 상세 진단 명령의 원본 검사는 그대로 유지한다.

**자료 검사 완료는 모든 종목의 매수 가능을 뜻하지 않는다.** 과거 분봉 부족 종목은 제외하고, 당일 분봉·최신 호가·시장·RVOL·전략 조건은 이후 평가에서도 계속 검사한다. 확보되지 않은 당일 자료가 있으면 해당 종목은 조건을 통과할 수 없다. 장전/주말에는 아직 없는 당일 봉을 만들지 않는다. 개장 후 75분 대기는 그대로이며, 예를 들어 오후 12시에 켰다고 추가로 75분을 기다리는 것은 아니다. 당일 개장 이후 자료를 확보한 뒤 원래 매수 가능 시간과 조건을 적용한다.

별도 터미널의 `paper-status --config config/sessionquant.realtime-paper.example.yaml`에서도 `warmup` 진행률·기준 시각·남은 누락을 확인할 수 있다. `engine.data_ready`는 예열 검사 종료 여부이며 실시간 거래 가능 승인이나 실계좌 검증이 아니다. 수동 `history-backfill`은 선택적 사전 준비/진단용으로 남으며 실행 엔진을 중지한 상태에서만 사용한다.

```powershell
python -m sessionquant run --config config/sessionquant.realtime-paper.example.yaml
```

브라우저에서 **http://localhost:8501**에 접속하고 **모의매매** 표시를 확인한다. 합성 데모는 별도 경고로 구분한다. 초기 가상 현금은 $100이다. 실제 계좌 보유/현금은 사용하지 않으며 이 예시에서는 실제 계좌 조회도 꺼져 있다. **자료 준비 검사 종료 후 매매 시작**을 열고 확인란을 선택한 뒤 시작을 요청해야 신규 진입을 판단한다. 기다리는 동안에도 수집은 계속된다.

홈은 운영형으로 시세·종목·뉴스·AI 상태, 모의 총자산·매수 가능 금액, 보유 종목을 표시한다. 왼쪽 메뉴로 상세 화면을 연다. 감시 목록을 기다릴 때는 **목록 대기**, 구간 수가 정해지면 **분봉 확인 · 40 / 88구간**처럼 표시한다. **시스템·설정 → 자료 준비 자세히**에서 재사용·보충·제외 근거를 확인한다. 시세의 **최근 수신**은 엔진 연결과 최근 호가 일부를 확인한 상태이며 전체 종목의 실시간 권한을 뜻하지 않는다.

화면은 선택한 메뉴에 필요한 기록만 조회한다. **시장·종목**은 현재 상태와 최근 호가·기술 분석 각 300건, 시장 방향 1건, 경제 일정 200건, 일별 참고 지표 30건을 읽으며 원본 분봉과 뉴스 본문은 읽지 않는다. 기술 분석 이력은 최근 300건 안에서 종목별 마지막 평가를 표시한다. 현재 감시·집중 목록은 별도로 저장된 최신 상태를 사용한다. 매매 내역의 주문·체결과 뉴스 상세의 수신 집계는 기존 최대 2,000건 범위를 유지한다.

**메인은 보이는데 상세 화면에 DB 오류가 나면:** MySQL `2013`은 조회 중 연결이 끊겼다는 뜻이며, 장전이거나 시세가 없다는 뜻은 아니다. 이전 버전은 상세 메뉴마다 쓰지 않는 기록까지 22종류×2,000건씩 읽고, 한 번 실패하면 먼저 읽은 자료도 전부 비웠다. 현재 버전은 시장·종목에서 먼저 읽은 자료를 남기고 나머지는 **조회 미완료**로 표시한다. 신호 조회 실패를 신호 0개로 표시하지 않으며 다음 새로고침에서 새 연결로 다시 읽는다. 거래 제어가 있는 화면은 조회 실패 시 제어 버튼을 표시하지 않는다. 문제가 계속되면 앱 로그의 `dashboard_read_failed`에 있는 `source`(실패한 기록), `elapsed_seconds`(걸린 초), `mysql_code`를 확인한다. 접속 비밀번호와 원문 SQL은 이 진단 로그에 남기지 않는다. 컨테이너의 `healthy` 표시는 화면 서버 응답을 뜻하며 DB 조회 성공까지 보장하지 않는다.

**전체 매도**는 새 매수를 막고 관리 포지션을 청산하는 요청이다. 확인 절차와 미체결 처리를 유지한다. 개별 종목 매도·주문·체결은 **매매 내역**, 월 AI 비용·월 한도액·수동 충전 메모는 **뉴스·LLM → LLM 사용량**에서 확인한다.

- 정규장 개장 후 75분부터 신규 진입을 허용한다. 5분/15분 확정봉, 강세장, 유동성·스프레드·RVOL·전략 신호·위험 예산을 모두 통과해야 한다. 신호가 없으면 거래 0건이 정상이다.
- 75분은 토스의 주문 시간 제한이나 프로그램 실행 후 타이머가 아니다. 기존 04단계 시간표를 유지하며 현재 기술 전략은 당일 5분봉 최소 15개와 ATR14를 요구한다. 이 구현의 ATR14는 이전 종가와 비교하는 14개 구간을 위해 봉 15개(75분)가 필요하다. 시작 시각만 앞당겨도 지표 부족 검사를 통과하지 못한다. 더 이른 진입은 지표 기간/전일 자료 사용 방식까지 별도 검증해야 하며 75분을 최적값으로 검증한 것은 아니다.
- 최대 50−n개 운영 후보에서 최대 20개를 집중 분석하고, 권장 보유 수는 2개다. 소수점 시장가 체결은 가상의 지연·호가 유동성·슬리피지·수수료를 적용한다.
- 일반적인 16:00 미국 동부시간 폐장일에는 13:30 신규/추가매수 마감, 14:40 청산 시작, 15:00 소수점 접수 마감이다. 조기 폐장은 달력에 따라 앞당긴다.
- 전량 매도/매매 종료를 요청했다면 **체결과 잔량 0을 확인한 뒤** 프로그램을 종료한다. 프로세스가 꺼진 동안에는 시세·모의 손절·청산을 처리할 수 없다.
- 모의매매의 전체 종료·청산 후 보유 수량과 미체결 주문이 모두 없어지면 **매매 재개**에서 확인란을 선택해 다시 시작할 수 있다. 앱 재시작이나 장부 초기화는 필요 없다. 자금·누적 손익·일일 위험 제한·이미 사용한 신호는 유지되며 거래 시간과 자료 조건도 다시 적용된다. 청산 진행 중·예열 중·완료된 실행과 실거래에는 이 재개 경로를 열지 않는다. 매매 종료는 신규 매수만 잠시 멈추는 기능이 아니라 전체 청산 요청이다.
- 소수점 접수 마감 뒤 남은 수량도 유효한 최신 호가로 평가금액을 갱신한다. 이때 모의 체결은 발생하지 않으며, 평가금액 갱신을 청산 완료로 해석하지 않는다.
- 같은 종목을 매도한 뒤 다시 보유하면 전량 매도를 다시 요청할 수 있다. 현재 매도 처리나 요청이 진행 중일 때는 중복 요청을 막는다.

실행 중 별도 터미널에서 외부 호출 없이 요약을 확인할 수 있다.

```powershell
python -m sessionquant paper-status --config config/sessionquant.realtime-paper.example.yaml
python -m sessionquant paper-status --config config/sessionquant.realtime-paper.example.yaml --output paper-status-after-close.json
```

`engine.heartbeat_fresh`는 엔진 연결, `market.quote_fresh_count`는 최근 호가, `strategy_rvol_count`는 현재 전략 전달값, `blocker_counts`는 진입 차단 사유다. `latest_candidates`는 각 평가 시각의 결정이며 현재 유효함을 뜻하지 않는다. `namespace_totals`는 **원장 전체 누계**이며 오늘만의 결과가 아니다. 명령이 보고하는 `order_writes: 0`, `llm_generation_calls: 0`은 상태 조회 자체가 외부 호출/주문을 하지 않았다는 의미다.

대시보드에서는 시장 데이터 표의 **Paper 거래 조건·Paper 가정·전략에 전달한 RVOL·전략 RVOL 근거 상태**를 확인한다. 실제 계좌 자격/RVOL 비교 근거 확보율이 0이어도 Paper 실험 전달값은 별도로 표시한다. 뉴스 분석 화면에서는 기사→분석→호출·오류·토큰/추정 비용을, 거래/전략 화면에서는 후보 차단→신호→주문→가상 체결→청산 사유를 확인한다.

## 주말에 분봉·뉴스 동작 확인

실행 중에도 별도 터미널에서 아래 두 명령을 사용할 수 있다. **실행 프로그램과 같은 설정 파일**을 지정한다. 이미 준비한 원장에는 `prepare-paper`를 다시 실행하지 않는다.

```powershell
python -m sessionquant history-status --config config/sessionquant.realtime-paper.example.yaml --details --output history-check-01.json
python -m sessionquant news-status --config config/sessionquant.realtime-paper.example.yaml --output news-check-01.json
```

출력은 짧은 요약으로 표시하고 상세 내용은 JSON 파일에 저장한다. 파일이 이미 있으면 `02` 등 새 이름을 사용한다. 두 명령은 저장된 자료를 읽으며 토스/뉴스 API 요청, 유료 AI 생성, 주문을 하지 않는다. 과거 분봉 준비 상태와 장중 현재 RVOL은 별개이며 주말에 현재 RVOL이 비어 있어도 과거 자료가 사라졌다는 뜻은 아니다.

- `history_readiness_preview`: 다음 운영일에 사용할 분봉 준비 종목과 제외 사유. `history_quality`: 날짜별 누락·충돌. 복사된 분봉에 과거 수집 진행표가 없으면 현재 저장된 시총 후보와 달력으로 검사 범위를 정한다. 원본 기록은 바꾸지 않는다.
- `counts.news_receipts`: 최근 기사 수신 횟수(중복 포함). `llm_request_attempts`: 실제 생성 요청 시도. `validated_responses`: 응답 형식·근거 검사 통과. `cache_hits`: 이전 분석 재사용으로 새 유료 요청이 아니다.
- `providers`: 공급자별 최근 시도/성공/오류. `pre_llm_exclusions`: 오래된 기사·본문 부족 등 분석 전 제외 사유. `latest_calls`: 최근 요청의 분류·이유·원문 근거와 검사 실패 항목(`failed_field`).
- 조회 범위는 최근 24시간 중 수신 최대 2,000건, 분석 처리 기록 최대 500건, 실제 AI 요청 최대 500건이다. 실제 요청을 별도로 조회하므로 본문 부족 등의 제외 기록이 많아도 요청 이력이 밀려나지 않는다. 전체 누계는 아니며, 조회 한도 도달 여부는 `scope`에 표시한다. 메인 화면은 처리 기록과 실제 요청을 각각 최대 300건 조회한다.

홈의 **뉴스·AI 분석 카드**에서 고유 기사 수·분석 완료·실패 건수를 확인한다. 왼쪽 **뉴스·LLM**에서 요청·실패·대기·제외 사유와 **분류 이유와 원문 근거**를 볼 수 있다. 홈 수치는 최근 24시간의 제한된 조회 범위이며 현재 연결 정상이나 전체 누계를 뜻하지 않는다. 자동 갱신을 켜면 메인의 시세·보유 상태는 5초, 뉴스·AI 요약은 별도로 60초마다 읽는다. 시장·종목은 위쪽에서 선택한 표만 10초마다 읽으며, 처리 속도·분석 이력은 수동으로 확인한다. 뉴스·LLM은 30초, 다른 화면은 수동 갱신이다. 원본 JSON은 왼쪽 ‘원본 기록도 보기’를 켰을 때만 표시한다. 자동 갱신을 꺼도 수집·매매 엔진은 계속 실행된다. 뉴스 상세는 선택한 기업 뉴스·경제 뉴스·LLM 사용량만 읽으며 공통 요약의 조회 범위는 유지한다. 화면 조회 자체는 뉴스를 수집하거나 AI를 호출하지 않는다.

주말에도 뉴스 작업은 실행되지만 새롭고 분석 가능한 기사가 없으면 AI 요청 0건일 수 있다. **분석 완료는 분류가 정답이라는 뜻이 아니다.** 회사 영향·주주 영향·확인된 내용/소문·원문 인용을 기사와 비교해야 한다. 이 도구는 분류 정답률을 만들어 표시하지 않는다.

## 4. 장 마감 후 전략 실행 분석

Paper 잔량을 정리하고 엔진을 중지한 뒤 실행한다. 경로는 매번 새 이름을 사용한다.

```powershell
python -m sessionquant record-export --config config/sessionquant.realtime-paper.example.yaml --out data/paper-session-review-01
python -m sessionquant record-quality --bundle data/paper-session-review-01
python -m sessionquant replay-recording --bundle data/paper-session-review-01 --db data/paper-session-replay-01.db
python -m sessionquant evaluate-candidates --help
python -m sessionquant evaluate-recording --help
```

재생은 기록 당시 수신·분석 완료 시각, 일일 감시 대상, Paper 정책과 RVOL 가정을 유지하며 외부 API/LLM을 다시 호출하지 않는다. 거래 조건이 다른 원장의 재시작이나 혼합 정책 기록은 거부한다. 초기 포지션이 없는 시점부터 완전하게 기록해야 재생할 수 있다.

우선 확인할 것은 실제 수익률보다 **진입 조건이 충족됐는지, 뉴스 근거가 판단 시점에 이미 있었는지, 주문과 체결이 구분되는지, 손절/당일 청산이 실행됐는지**다. [후보 선정 검증](archive/stages/STAGE08_CANDIDATES.md)과 [실데이터 기록 연구](archive/stages/STAGE05_RECORDING_BACKTEST.md)의 비교 명령으로 뉴스 가점 유무·전략 차이를 분석할 수 있다. 하루의 거래 결과는 전략 수익성 검증으로 간주하지 않는다.

## Paper 조건과 유지되는 제한

기본값은 여전히 `paper_data_policy: strict`다. 새 예시만 `observed_paper_v1`을 사용한다.

| 입력 | 실데이터 Paper 처리 |
| --- | --- |
| 실제 계좌 거래 가능·소수점 지원 미확인 | 실제 권한은 UNKNOWN 그대로 저장하고 가상의 소수점 거래를 허용 |
| 상장 상태·거래소 | 24시간 이내 수신하고 유효기간이 남은 ACTIVE·지원 거래소 근거 필요 |
| 거래 불가·소수점 불가·거래정지·기업행동이 명확히 확인됨 | 신규 진입 및 Paper 매수 체결 차단 |
| 거래정지·기업행동 상태 미확인 | 미확인 가정을 기록. 최신 정상 호가·분봉 검사는 계속 필요 |
| 동일 제공처·가격 조정 방식·20거래일 동일 경과 분의 완전한 거래량 | 계산 RVOL 사용. 분할 비교 근거가 없으면 `EXPERIMENTAL_UNVERIFIED`로 표시 |
| 분봉 누락/충돌·출처 혼합·비교 거래량 0·시세 만료 | 계산/신규 진입 계속 차단. 보간이나 RVOL 상수 대체 없음 |

원본 적격성, `Quote.tradable`, 검증된 RVOL 필드를 true/VERIFIED로 바꾸지 않는다. 주문 의도와 연구 기록에 실제 적용한 정책·가정·RVOL을 남긴다. 모든 전략 주문은 `PaperBroker`로만 전달한다. 새 정책은 `market_v2` 모의 체결에만 적용한다.

## 검증 결과를 읽는 방법

자동 테스트에서는 합성 시세와 모의 뉴스·LLM 응답으로 수집부터 전략 판단, 체결, 손절·청산, 기록 재생까지 검사한다. 실제 사용자의 시세 지연이나 뉴스 분류 정확도, 장기간 전략 성과는 로컬 운영 기록으로 별도 확인해야 한다. 최신 자동 검사 기준은 [개발 인수인계](../HANDOFF.md)에 남긴다.

## 집중 종목이 계속 0개일 때

예열 완료와 매매 시작은 실제 매수와 다르다. 집중 선정에는 종목과 SPY의 서로 다른 시점 가격 2회, 최신 거래대금 자료가 필요하다. 첫 가격만 받았거나 공급자의 거래대금 순위에 해당 종목이 없으면 집중 대상이 되지 않는다. 집중 대상이 된 뒤에도 분봉·RVOL·전략·위험 조건을 따로 검사한다.

보유 종목 위험 관리와 예열 뒤에 집중 선정용 조회 시간을 따로 확보한다. 현재가·거래대금으로 후보를 정한 뒤, 후보 분봉을 먼저 준비하고 최신 호가를 받아 함께 판단한다. 추가 ETF 참고 자료와 배경 분봉은 뒤에서 조회한다. `max_cycle_seconds`(기본 15초)는 이 후보·배경 조회 구간의 요청 시간 한도로 사용하며, 앞선 위험 관리·예열 및 동기 저장 시간을 포함한 전체 회차가 15초 이내라는 뜻은 아니다. 실제 API 재시도까지 포함하는 주기 호출 한도와 공급자의 재조회 대기 시간은 유지한다.

시간·요청 한도 때문에 실행하지 못한 조회는 성공이나 실제 조회 시도로 처리하지 않는다. 특히 거래대금 조회가 생략돼도 다음 회차에서 다시 시도할 수 있다. 이 수정은 코드에서 재현한 조회 누락 경로를 해결하며, 과거 장중 집중 0의 원인이 전부 같았다는 뜻은 아니다.

장중 적용 확인:

1. **시장·종목**에서 집중 제외 이유를 확인한다. `종목 현재가 미수신`, `종목 비교 가격 1회 부족`, `시장(SPY) 현재가 미수신`, `거래대금 미확인`, `관찰 자료 지연·미래 시각`을 구분한다.
2. **시세·거래 적격성·RVOL 데이터 품질 → 우선 조회·요청 지연·과거 봉 보충 근거**에서 `토스 현재가 일괄 조회`, `토스 거래대금 순위`의 요청 여부와 시각을 확인한다. `시간 부족으로 조회 대기`와 실제 API 오류는 다르다.
3. 두 시점의 유효한 가격·시장 비교·거래대금이 모이면 집중 목록과 종목 판단 기록이 생기는지 확인한다. 주문 0건만으로 수집 실패로 판단하지 말고, 이후 전략 차단 사유도 확인한다.

원본 수집 상태에는 `pre_focus_phase_seconds`(후보 조회 전까지), `focus_phase_seconds`(후보 조회·전달), `read_measurements`(실제 요청·생략), `candidate_delivered_at`(후보 엔진 전달)이 남는다. `priority_delivered_at`은 위험 관리 자료 전달 시각으로 구분한다. 실제 운영에서 지속되는 지연은 이 기록으로 추가 측정해야 한다.

GCP에서는 소스 파일을 갱신한 뒤 `docker build -t sessionquant:local .`로 이미지를 다시 만들고 앱을 재시작해야 반영된다. 운영 중 매매를 중단하지 않도록 장전·매매 시작 버튼을 누르기 전에 적용한다. 기존 저장 공간 수정과 `.env` 파일은 보존하며, Git 충돌이 나면 강제 초기화하지 않는다.

## 처리 지연 확인과 중복 작업 개선

후보 수집의 요청 시간 중 마지막 `min(5초, max_cycle_seconds / 2)`를 상세 호가용으로 남긴다. 기본 15초에서는 앞선 현재가·순위·분봉 요청이 마지막 5초까지 소비하지 못한다. 이 때문에 생략한 요청은 `quote_time_reserved`로 기록하며, 전체 시간이 실제로 끝난 `deadline_skipped`와 구분한다. 호출 횟수·재시도·429 대기 한도는 공유하고 저장·엔진 작업 시간을 제외하는 기존 계산 방식도 유지한다. 느린 응답·호출 한도 때문에 모든 후보의 호가를 매회 받을 수 있다는 보장은 아니다.

같은 엔진 처리 묶음에서는 SPY·QQQ 시장 판단을 한 번 계산해 공유한다. 평가 시각·호가 유효시간 설정이 바뀌거나 SPY·QQQ 입력이 갱신되면 다시 계산한다. 묶음 종료·오류 시 계산 결과를 버리므로 다음 묶음으로 신선도를 연장하지 않는다.

2026-11-18에는 입력 전달 순서로 정상 자료가 매수 판단에서 빠지던 경로를 수정했다. 후보 분봉 준비 후 최신 호가를 받아 판단하며, 늦게 도착한 분봉·상장 정보도 원본 시각을 유지한 채 반영한다. 유효한 호가가 남아 있으면 분봉 도착 때 다시 판단한다. 배경 분봉 조회와 집중 호가 조회의 순서를 별도로 관리해 배경 수집이 집중 분석을 미루지 않게 한다.

전략의 RVOL과 분봉 연속성은 같은 확정 5분봉 종료 시각을 기준으로 검사한다. 다음 1분봉이 아직 도착하지 않은 것과 전략에 필요한 구간이 실제로 비어 있는 것을 구분한다. 최신 분봉 90초, 시장 판단 호가 30초, 후보 선정·모의 체결 호가 10초 등 기존 유효시간은 유지한다. SPY·QQQ는 당일 분석 구간을 우선하며 종목 RVOL용 과거 20일을 채우려는 불필요한 추가 조회를 멈춘다.

**시장·종목 → 집중 목록 → 최종 후보 → Paper 진입 승인**에서 종목별 시장 방향, 전략 RVOL, 전략 대기 조건, 주문 차단 이유를 함께 확인한다. 예를 들어 RVOL이 계산돼도 상승 추세·두 조정봉·반등 거래량이 없으면 매수하지 않는다. 만료된 표는 이전 평가로 표시한다. 전체 감시목록의 매분 RVOL 표와 실제 후보의 확정봉 기준 RVOL은 기준 시각이 다르다.

집중 수를 줄이면 종목별 상세 호가를 다시 받는 시간이 짧아진다. 감시목록 전체 분봉 수집량이 같은 비율로 줄어드는 것은 아니다. 현재 기본 집중 수 20은 유지하며, 실제 수집 주기와 후보 호가 유효시간을 함께 보고 조정한다. 동시 조회는 공급자 호출 제한을 넘기는 수단이 아니며, 주문·잔고 갱신은 순서를 유지해야 한다.

2026-11-17에는 큰 저장 자료의 JSON 변환을 반복하던 부분과 분봉의 불필요한 전체 재저장을 줄였다. 새 분봉·정정 값·더 이른 수신 시각·수집 진행 변경은 계속 저장한다. 지표 계산에서는 같은 시점에 검증한 분봉 목록을 5분봉·15분봉·평균 거래가격 계산에 함께 사용한다. 수신 시각, 누락·정정 충돌, 금액 소수 정밀도와 매수 제한은 유지한다.

장 마감 후 자동 종료를 기다리는 동안에는 다음 날 예열과 배경 수집을 시작하지 않는다. 당일의 확정 운영 목록을 유지하면서 보유 종목 위험 호가·청산 관리는 계속한다. 다음 거래일 준비 및 명시적인 `history-backfill` 명령의 달력 기준은 그대로다.

**시장·종목 → 시세·거래 적격성·RVOL 데이터 품질 → 처리 속도 확인**에서 다음을 볼 수 있다.

| 표시 | 확인할 내용 |
| --- | --- |
| API 호출 간격·응답·재시도 대기 | 제공처 제한 때문에 기다리는지, 응답 자체가 늦는지 |
| DB 요청·응답 / DB 저장 확정 | MySQL 요청과 커밋에 걸린 시간 |
| DB 자료 변환 / 분봉 합치기·저장 | 자료를 정리하고 저장하는 비용 |
| 매매 지표 / RVOL / 분봉 품질 검사 | 계산에 걸린 시간 |
| 엔진 판단·저장 / 예열 / 감시 목록 저장 | 큰 처리 단계의 소요 시간 |

최근 수집 회차와 **현재 프로세스에서 가장 느렸던 3회**만 `market_performance_v1`에 보존한다. 전체 이력을 계속 쌓지 않으며, 재시작하면 느린 회차 목록은 새로 시작한다. 최신 화면에는 느린 회차의 시각과 전체 시간이 나오고, DB 원본에는 해당 회차의 단계별 측정도 남는다. SQL·인증정보·기사 본문은 계측에 넣지 않는다.

측정 범위는 시장 수집 작업과 그 안에서 전달한 엔진 처리다. 별도 뉴스 작업·수집 밖의 엔진 tick 전체를 각각 추적하는 프로파일러는 아니다. 단계 시간이 서로 포함될 수 있어 합산하면 안 된다. HTTP 대기에는 같은 이벤트 루프의 다른 작업에 밀린 시간도 포함될 수 있고, 프로세스 CPU 시간에는 동시 뉴스 작업도 포함된다. SQLite에서는 DB 요청·응답 시간을 별도 측정하지 않는다.

오프라인 비교는 다음 명령으로 실행한다. 임시 SQLite DB에 합성 분봉 20거래일 7,800개와 당일 3종목 자료를 넣고, 수집 후 저장·엔진 판단·연구 기록·RVOL 표시를 반복한다. 실제 API·LLM·운영 DB는 사용하지 않는다.

```bash
python -m scripts.benchmark_market_pipeline --cycles 5 --output performance-check-01.json
```

개발 환경의 동일 입력 5회 비교(한 번의 측정 예시):

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 처리 시간 합계 | 4.17초 | 0.94초 |
| 반복 조회 중 과거/당일 분봉 저장 | 15회 | 3회 |
| 계산·후보 판단 결과 해시 | 동일 | 동일 |
| API 호출·주문 | 0건 | 0건 |

이 수치는 GCP 장중 전체 회차의 예상 속도가 아니다. 이전에 관측한 약 11초 간격의 원인을 이 합성 시험만으로 확정하지 않는다. 서버 적용 후에는 새 계측으로 실제 DB·대기·계산 비중을 확인한다. 호출 속도 제한과 단일 엔진 작성자 구조는 유지한다.


## 화면 상태를 읽는 법

- **자동매매 켜짐**: 조건을 계속 평가하도록 사용자가 허용한 상태다. 실제 주문이 발생했다는 뜻은 아니다. 홈의 최근 모의 체결과 매매 내역의 주문·체결을 따로 확인한다.
- **집중 0개**: 시장·종목에서 운영 후보들의 주요 제외 이유를 확인한다. 현재가 미수신, 비교 가격 1회 부족, 거래대금 미확인 등을 구분한다. 자료가 충분해도 순위·전략 조건에 따라 거래가 없을 수 있다.
- **시장 참고 ETF의 관측 가격**: 받은 현재가·확정 분봉 종가·호가 중간값을 종류와 시각으로 구분한다. 오래된 값은 과거 기록으로 표시한다. **분석 상태**는 별도이며, 가격만 받았다고 권한·신선도·비교 가능성 검증을 통과한 것으로 바꾸지 않는다. 확인되지 않은 등락률은 비워 둔다.

장중에는 처리 속도 확인에서 후보 조회가 생략되는지, API·DB·지표 계산 중 어디에 시간이 걸리는지 함께 확인한다. 신규 매수는 여전히 미국 동부시간 10:45~13:30이며 이번 장전 수정으로 전략의 자료 요건을 완화하지 않았다.
