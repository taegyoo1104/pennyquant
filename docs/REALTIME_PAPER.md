# 실제 시세로 모의매매 운영하기

이 문서는 **`config/sessionquant.strategy-lab-websocket.example.yaml`**을 사용하는 일상 운영 안내입니다. 처음 설치는 [시작 안내](GETTING_STARTED.md), GCP 명령은 [GCP 운영](GCP_PAPER.md), 전략의 정확한 기준은 [매매 과정](TRADING_PROCESS.md)을 먼저 확인하세요.

실제 토스 시세와 실제 뉴스를 사용하지만 주문·현금·보유는 Paper 모의 장부입니다. 이 프로젝트의 확인 목표는 수익률보다 **전략 조건 → 판단 → 주문 → 체결 → 청산이 의도한 순서로 기록되는가**입니다.

## 어떤 설정을 사용하나요?

| 프로필 | 용도 | 핵심 차이 |
| --- | --- | --- |
| `strategy-lab-websocket` | 현재 권장 실데이터 모의 운영 | 웹소켓 호가, 단순 눌림목, 거래대금 집중 최대 10개·30분 재선정 |
| `strategy-lab` | REST 방식과 비교·진단 | 같은 단순 전략을 REST 호가로 운영. 별도 장부 사용 |
| `realtime-paper` | 이전의 엄격한 전략·자료 조건을 비교하는 고급 설정 | 기존 눌림목·RVOL·시장 필터와 과거 분봉 준비 조건 유지 |

위 이름은 `config/sessionquant.<이름>.example.yaml`을 줄여 쓴 것입니다. CLI와 GCP Compose의 일부 **기본값은 이전 설정**이므로 파일명을 명시합니다. 추천 설정이 바뀌었다고 이미 실행 중인 GCP의 설정·이미지가 자동으로 바뀌지는 않습니다.

권장 프로필은 `observed_paper_v1` 정책과 초기 가상 현금 $100을 사용합니다. 실제 계좌 자격 미확인은 그대로 남기고 모의 소수점 거래 가정을 기록합니다. 명확한 거래 불가·거래정지, 만료 시세, 분봉 누락, 자금·위험 한도는 계속 검사합니다. 실제 거래 권한을 확인한 것으로 바꾸지 않습니다.

## 매일의 흐름

1. **장전 실행:** 같은 설정·장부로 엔진을 켭니다. GCP는 VM 시작과 프로그램 시작을 [별도로 확인](GCP_PAPER.md#매일-켜고-접속하기)합니다.
2. **자료 확인:** 메인 화면에서 연결, 집중 감시 종목, 관측 가격의 시각을 봅니다. 장전에는 오늘 정규장 봉과 전략 판단이 대기여도 정상입니다.
3. **매매 시작:** 자료 준비가 끝나면 확인란을 선택해 요청합니다. `자동매매 켜짐`은 조건 평가를 허용했다는 뜻이며 체결 완료가 아닙니다.
4. **장중 확인:** 집중 카드의 단계와 **시장·종목 → 매수 판단**을 봅니다. 주문이 생기면 **매매 내역**에서 체결과 잔량을 구분합니다.
5. **종료 확인:** 전체 매도·매매 종료를 요청했다면 보유·미체결이 정리됐는지 봅니다. GCP 자동 종료 후에는 VM 중지와 새 백업 성공을 각각 확인합니다.

로컬 실행 명령입니다. 설치 때 정한 `SQ_DB_NAMESPACE=sessionquant-strategy-lab-ws-v1` 환경도 유지합니다.

```powershell
python -m sessionquant run --config config/sessionquant.strategy-lab-websocket.example.yaml
```

오래된 가격과 판단은 과거 기록 또는 갱신 대기로 표시합니다. 카드의 `반등 확인`과 `모의 주문 승인`도 체결 완료와는 다릅니다. 정확한 주문·체결 결과는 장부에서 확인합니다. **최신 시세 확보율과 RVOL 확보율이 모두 100%여야 하는 하나의 진행률은 아닙니다.** 권장 단순 전략은 RVOL을 필수 진입 조건으로 사용하지 않습니다.

메인의 시세·보유는 5초, 뉴스·AI 요약은 60초마다 별도로 읽습니다. 시장·종목의 선택한 표는 10초, 뉴스·LLM은 30초이며 처리 속도·분석 이력과 나머지 화면은 수동 갱신입니다. 자동 갱신을 꺼도 엔진은 계속 실행됩니다. 화면을 읽는 동작 자체가 뉴스 수집이나 LLM 호출을 실행하지는 않습니다.

## 자료 준비와 거래 시간

권장 프로필은 **과거 RVOL 분봉이 부족하다는 이유만으로 시총 후보를 모두 제외하지 않습니다.** 이 프로필은 이전의 20거래일 예열 절차를 사용하지 않습니다. 시총 후보를 확인하고 필요한 당일 자료를 준비하며, 실제 진입에는 당일 확정 5분봉·15분봉과 ATR 자료가 필요합니다. 없는 봉을 만들어 채우거나 오래된 호가를 최신으로 바꾸지 않습니다.

집중 선정은 상승 추세를 통과한 종목을 고르는 단계가 아닙니다. 거래대금으로 관찰할 종목을 정한 뒤 최신 확정봉에서 전략을 평가합니다. 정규장 개장 기준 30분 슬롯 동안 순위 변동만으로 계속 교체하지 않으며, 자료 유효성·거래 가능 상태 같은 안전 조건은 따로 확인합니다. 순위는 토스의 일간 거래대금 자료를 쓰며 최근 30분 거래대금이라는 뜻은 아닙니다. 경계 시점의 조정·반등 종목은 유지될 수 있고 자료 지연 시 재선정은 최대 120초 기다립니다. 관찰 명단을 유지하더라도 자료가 오래되면 신규 진입은 막습니다. 보유·미체결·청산 대기 종목은 집중 목록 밖에서도 위험 관리를 계속합니다.

현재 신규 진입은 **개장 75분 후부터**입니다. 프로그램을 켠 시점이나 집중 편입 시점부터 75분을 새로 기다리는 것은 아닙니다. ATR14 계산에 필요한 당일 5분봉 15개를 유지하기 때문입니다. 이미 수집한 봉으로 판단하므로 집중 편입 후 추세용 30분을 무조건 다시 기다리지도 않습니다.

일반 16:00 미국 동부시간 폐장일에는 신규·추가매수 마감 13:30, 청산 시작 14:40, 소수점 접수 마감 15:00을 사용합니다. 조기 폐장은 달력에 따라 앞당깁니다. 13:00 조기 폐장일은 현재 시간표상 신규 진입 구간이 없습니다. 단순 전략으로 바꿔도 이 시간표와 위험 한도를 없애지 않았습니다.

예열 완료는 검사 종료이며 모든 종목의 매수 허가가 아닙니다. 새 시세와 봉이 오면 조건을 다시 평가하므로 숫자가 변할 수 있습니다. 프로그램 재시작은 저장 자료를 재사용하지만 장부 복원·최신성 확인과 누락 보충까지 생략하지는 않습니다.

## 상태를 파일로 보내려면

실행 중인 엔진과 **같은 설정·DB 환경변수**를 사용하는 별도 터미널에서 아래를 실행합니다. 저장 기록만 읽으며 토스 토큰 발급·뉴스 수집·LLM 생성·주문을 하지 않습니다.

```powershell
python -m sessionquant paper-status --config config/sessionquant.strategy-lab-websocket.example.yaml --output paper-status-01.json
python -m sessionquant history-status --config config/sessionquant.strategy-lab-websocket.example.yaml --details --output history-status-01.json
python -m sessionquant news-status --config config/sessionquant.strategy-lab-websocket.example.yaml --output news-status-01.json
```

파일이 이미 있으면 `02`처럼 새 이름을 사용합니다. GCP에서는 [실행 중 점검 명령](WEBSOCKET_ROLLOUT.md#실행-중-점검)을 사용하세요.

- `engine.heartbeat_fresh`: 엔진의 최근 응답 여부입니다.
- `quote_transport`, `websocket`: 선택한 호가 경로와 연결·수신·전달 상태입니다. [웹소켓 지표 해석](WEBSOCKET_ROLLOUT.md#실행-중-점검)을 참고합니다.
- `latest_candidates`, `blocker_counts`: 평가 당시 후보와 차단 사유입니다. 평가 시각을 함께 봅니다.
- `namespace_totals`: 해당 장부 전체 누계입니다. 오늘만의 결과가 아닙니다.
- `order_writes: 0`, `llm_generation_calls: 0`: 이 상태 조회 명령이 주문·유료 생성을 하지 않았다는 의미입니다.

## CSV 대신 약 5분간 연속 진단

서로 다른 시각에 내려받은 표만으로 지연 원인을 비교하기 어려울 때 사용한다. `scripts/check_market_freshness.py`는 엔진 상태·집중 목록·호가 시각·분봉 누락·RVOL·후보 차단 사유·처리 시간을 한 번의 읽기 전용 SQL 조회로 함께 기록한다. 각 자료가 만들어진 원래 시각도 보존한다. 한 번에 조회했다고 모든 자료가 동시에 갱신된 것은 아니다.

최신 진단 파일이 있는 **운영 VM의 별도 SSH 또는 tmux 터미널**에서 실행한다. 이 파일은 표준입력으로 실행되므로 앱 이미지 재빌드나 엔진 재시작이 필요 없다. 기본적으로 컨테이너의 `SQ_SESSION_CONFIG`를 따라 현재 실행 중인 웹소켓·REST 프로필의 장부를 읽으며, 별도 장부를 조사할 때만 `--config`로 설정을 지정한다.

```bash
umask 077
SQ_DIAG=$(mktemp "$HOME/sessionquant-diagnostic.XXXXXX.jsonl")
sudo -n docker compose -f /opt/sessionquant/deploy/gcp/compose.yaml exec -T app \
  python - --samples 31 --interval 10 \
  < /opt/sessionquant/scripts/check_market_freshness.py > "$SQ_DIAG"
SQ_DIAG_EXIT=$?
printf '진단 파일: %s\n종료 코드: %s\n' "$SQ_DIAG" "$SQ_DIAG_EXIT"
```

약 10초마다 31회 읽고 종료한다. 느린 DB 조회가 있으면 더 오래 걸릴 수 있다. 파일은 한 줄에 하나의 JSON을 담은 JSONL 형식이며 나중에 전달해도 수집 당시 시각을 확인할 수 있다. `--samples`는 1~61, `--interval`은 5~60초로 제한한다. 옵션 없이 실행하면 기존처럼 JSON 하나만 출력한다.

- `read_started_at`·`read_finished_at`·`db_read_seconds`: 진단 조회 자체에 걸린 시간이다. 엔진 처리 시간과 구분한다.
- `evaluated_at`·`evaluation_age_seconds`: 해당 종목을 실제로 평가했던 시각과 경과 시간이다. `strategy_rvol_saved`와 `rvol_at_last_evaluation`은 저장 당시 참고값이며 현재 매수 허용값이 아니다.
- `strategy_volume`·`minute_volume`: 전략의 확정 5분봉 기준 RVOL과 감시목록의 매분 RVOL이다. 각각의 `cutoff_at`과 누락 개수를 비교한다.
- `quote_age_on_receipt_seconds`·`seconds_since_quote_received`: 오래된 시세가 도착했는지, 수신 후 갱신이 늦었는지 구분한다.
- `performance`: 엔진이 마지막으로 저장한 회차의 단계별 시간이다. 같은 회차가 여러 번 기록될 수 있으며 중첩 단계의 시간을 합산하지 않는다.

조회 실패도 `FAILED` 표본으로 남기고 다음 회차에 새 연결로 다시 읽는다. 마지막 `summary`에 성공·실패·중단 횟수를 기록한다. 종료 코드 0은 수집 완료, 1은 일부 조회 실패, 130은 사용자의 중단이다. 수집 완료가 매매 조건 통과를 뜻하지 않는다. DB 쓰기·주문·Toss 인증/조회·LLM 호출은 없으며, 계좌·인증정보·뉴스 본문·원문 SQL·오류 본문도 출력하지 않는다. 이 진단 기능은 대시보드를 외부에 공개하거나 상시 원격 접속을 제공하지 않는다.

## 장 마감 백업에서 매수 차단 이유 확인

`scripts/review_paper_backup.py`는 Cloud Shell 등에서 백업을 네트워크 없는 임시 MySQL에 복원해 요약한다. 운영 VM이나 프로그램은 시작하지 않는다. `--since`·`--until`은 전체 조사 기간이며, 선택적으로 `--entry-since`·`--entry-until`을 함께 지정하면 해당 진입 시간대의 후보 평가만 별도 집계한다. 끝 시각은 포함하지 않는다. 시간대는 사용자가 선택한 조사 범위이며 실제 서버의 거래소 달력·진입 설정을 자동 판정한 값이 아니다.

`entry_review.selected_entry_window`에서 종목별 입력 차단(`decision_blockers`), 전략 조건 대기(`strategy_wait`), 후보 비교 차단(`selection_blockers`), 위험·자금 배분 거절(`allocation_reasons`)을 구분한다. RVOL은 계산된 값과 전략에 전달된 값, 과거 거래일 확보 수, 당일 중간·끝 누락 수와 기준 시각을 함께 남긴다. 모두 저장 당시 관측이며 새로 계산하거나 신선도를 연장하지 않는다. 경고는 공급원별로도 집계하며 원문 오류 메시지를 내보내지 않는다.

집계는 같은 종목의 반복 평가를 포함하고 차단 이유는 서로 겹친다. `signal_present`는 후보 평가에 남은 기술적 신호이며 신호 테이블·주문·체결 건수와 다르다. 신호 테이블 기록 전에 후보 선정에서 차단될 수 있다. 원본에 상세 평가가 없는 구버전 기록은 `batches_missing_decision_details`로 표시한다. 이 경우 빈 집계를 거래 조건 통과로 해석하지 않는다. 종목별 표본은 첫 2개와 마지막 4개로 제한한다.

백업 조회는 JSON 전체를 새 객체로 합치지 않고 필드별 HEX 열로 전달한다. `report_status: COMPLETE`는 조회한 행의 해석 완료이며, 매매 준비 완료를 뜻하지 않는다. 일부 행을 해석하지 못하면 `PARTIAL` 결과 파일을 저장하고 종료 코드 2를 반환한다. `transport`에는 표별 성공·실패 건수와 최대 20개의 실패 위치(표·행·필드·JSON 위치)를 남기며 원문 내용은 포함하지 않는다. 부분 결과의 0건을 실제 활동 없음으로 해석하지 않는다. 재시도할 때 남아 있는 백업 파일을 재사용할 수 있다.

## 뉴스와 LLM은 어떻게 확인하나요?

일반 `run` 실행은 **수집과 유료 분석을 분리**합니다. 장전에는 기사를 수집·저장하고,
같은 분석 대상의 제목·본문이 공백·대소문자 정리 후 동일한 경우 중복을 묶습니다.
내용이 달라진 기사나 다른 종목에 대한 판단은 합치지 않습니다. 장전에는 기업·시장 뉴스,
시장 맥락 설명과 AI 브리핑 모두 새 AI 요청을 보내지 않습니다.

개장 후에는 보유 종목 → 집중 종목 → 시장 뉴스 → 나머지 종목 순서로, 각 그룹에서 최신
기사를 먼저 분석합니다. **최소 5분 간격으로 최대 3개 분석 후보**를 처리하며 재시작해도
대기 목록과 처리 간격을 유지합니다. 수집 주기와 제공처 응답 시간 때문에 실제 간격은
더 길 수 있습니다. 일·시간·월 비용 제한은 그대로 적용합니다. 브리핑은 기존의 별도
정규장 일정으로 실행하며 기사를 새로 분석하는 작업과 구분합니다.

대기 목록은 최대 240개이며 넘치면 오래된 후보부터 제외합니다. 이는 **전체 기사 저장
한도가 아닙니다**. 목록에는 기존 수신 기록의 참조만 저장합니다. 기업 뉴스는 기본 24시간,
시장 뉴스는 기본 72시간 이내 자료만 분석하며, 처리 직전에도 게시 시각·본문·출처를 다시
검사합니다. 예산 부족이면 남은 자료를 보류하고, 그 외 실패는 최대 3회까지만 재시도합니다.
원문 본문을 보관하지 않는 발견형 뉴스는 정규장에서 선택됐을 때 허용된 원문을 다시
확인합니다. 휴장·조기 폐장·서머타임은 거래소 달력을 따릅니다.

메인과 뉴스 화면의 **뉴스 준비 상태**에서 대기 수와 미국 날짜 기준 중복·제외 수를 볼 수
있습니다. 이 숫자는 기사·종목별 분석 후보 기준이며, 아래 최근 24시간 조회 집계와 다릅니다.
오래된 상태는 ‘마지막 뉴스 준비 기록’으로 표시합니다. 조회 전용 대시보드는 수집·분석을
시작하지 않으며, 명시적으로 실행하는 아래 연결 진단은 일반 실행의 대기 목록과 별개입니다.

검증된 종목 뉴스 분석은 후보 우선순위의 가점에 사용하고, AI 브리핑은 저장된 판단을 설명합니다. 뉴스가 없거나 LLM이 실패했다고 가격 전략을 무조건 중단하지 않습니다. 확인된 악재·위험 차단은 별도이며 LLM이 주문 버튼을 대신 누르지 않습니다. 상세 역할은 [매매 과정](TRADING_PROCESS.md)에 정리했습니다.

홈의 기사·분석 숫자는 최근 24시간의 **제한된 조회 범위**입니다. 전체 누계나 현재 연결 정상 표시가 아닙니다. 자세한 범위는 `news-status.scope`에서 확인합니다. 중복 수신, 분석 전 제외, 실제 LLM 요청, 유효 응답, 캐시 재사용은 다른 수치입니다. `분석 완료`는 정답률 인증이 아니라 응답 형식·근거 검사를 통과했다는 뜻입니다.

원문 이용 권한, 본문 접근, API 제한 때문에 제목을 받았어도 분석하지 못할 수 있습니다. 특정 기업의 뉴스가 매일 나오리라는 보장도 없습니다. [뉴스 설정과 현실적인 제약](reference/NEWS_SETUP.md)을 확인하세요. OpenAI 충전 잔액과 프로그램의 월·일·시간 한도는 별개입니다.

선택적으로 **엔진을 중지한 뒤** 한 기업의 실제 뉴스→LLM 흐름을 점검할 수 있습니다.

```powershell
python -m sessionquant check-news --config config/sessionquant.strategy-lab-websocket.example.yaml --connect --provider openai
python -m sessionquant paper-news-probe --config config/sessionquant.strategy-lab-websocket.example.yaml --symbol NVDA
```

첫 명령은 모델 접근만 검사합니다. 두 번째는 실제 생성 요청을 실패 포함 최대 1회 시도하며 과금될 수 있습니다. 최신 원문·본문·종목 연결이나 예산이 없으면 요청하지 않습니다. 주문은 만들지 않습니다. 결과가 `VALID_RESPONSE_AND_STRATEGY_CONTEXT`이면 분석과 전략 맥락 연결까지 확인한 것이며, 거래 체결 성공을 뜻하지는 않습니다.

## 종료·재개·장 마감 기록

전체 매도·매매 종료는 신규 매수만 잠시 멈추는 기능이 아니라 청산 요청입니다. 보유 수량과 미체결이 모두 정리되면 **매매 재개**의 확인 절차로 다시 시작할 수 있습니다. 자금·누적 손익·일일 위험 한도·사용한 신호는 초기화하지 않습니다. 예열·청산 진행 중에는 재개하지 않습니다.

터미널에서 엔진을 끄면 그동안 시세 감시와 모의 손절을 실행할 수 없습니다. 소수점 접수 마감 후 남은 수량의 평가금액이 갱신돼도 청산된 것은 아닙니다. GCP 종료 절차는 잔량을 저장해 다음 실행에 복구하며 백업 성공을 확인한 뒤 조회 화면으로 전환합니다. VM은 자동으로 끄지 않습니다.

장 마감 후 엔진을 중지하고 기록을 내보내 재생할 수 있습니다. 매번 새 경로를 사용합니다.

```powershell
python -m sessionquant record-export --config config/sessionquant.strategy-lab-websocket.example.yaml --out data/paper-review-01
python -m sessionquant record-quality --bundle data/paper-review-01
python -m sessionquant replay-recording --bundle data/paper-review-01 --db data/paper-replay-01.db
```

재생은 당시 수신·분석 완료 시각과 Paper 정책을 보존하며 외부 API·LLM을 다시 호출하지 않습니다. 초기 포지션이 없는 시점부터 기록이 완전해야 하며, 혼합 정책 기록은 거부합니다. [기록 연구 상세](archive/stages/STAGE05_RECORDING_BACKTEST.md)와 `evaluate-candidates --help`도 참고할 수 있습니다.

## 문제별로 먼저 볼 것

| 현상 | 먼저 확인할 것 |
| --- | --- |
| 집중 0개 | 시총 목록 상태, 거래대금 수신 시각, 집중 제외 이유. 권장 프로필에 이전 SPY 비교 조건을 적용해 해석하지 않습니다. |
| RVOL만 0개 | 권장 단순 전략에서는 필수 조건이 아닙니다. 실제 차단 사유와 확정봉·호가를 확인합니다. |
| 모든 가격이 오래됨 | 웹소켓 연결·구독 수락·신선한 종목 수와 엔진 heartbeat를 확인합니다. 재연결이 분봉 준비까지 보장하지는 않습니다. |
| `DB 기록을 읽을 수 없습니다` | 시세 대기와 다른 오류입니다. 앱 로그의 `dashboard_read_failed`와 MySQL 오류 코드를 확인합니다. |
| 컨테이너는 healthy인데 표 오류 | healthy는 화면 서버 응답입니다. 모든 DB 조회 성공이나 전략 준비를 보증하지 않습니다. |
| 화면이 느림 | 자동 갱신을 잠시 끄고 처리 속도 표에서 API·DB·계산을 구분합니다. 터널 문제는 [GCP 안내](GCP_PAPER.md#대시보드가-안-열릴-때)로 확인합니다. |

시장·종목은 조회 일부가 실패하면 이미 읽은 자료를 남기고 나머지를 조회 미완료로 표시합니다. 조회 실패를 0건으로 해석하지 않습니다. 거래 제어 화면은 DB 조회 실패 시 버튼을 막습니다. 로그의 `source`, `elapsed_seconds`, `mysql_code`가 진단 근거이며 비밀번호나 원문 SQL을 공유할 필요는 없습니다.

처리 속도에는 API 응답·재시도 대기, DB 요청·커밋·자료 변환, 분봉 합치기, 지표 계산, 엔진 판단 시간이 남습니다. 단계가 서로 포함될 수 있어 합산하지 않습니다. 최근 회차와 현재 프로세스의 느린 3회만 보존하며, 재시작하면 느린 회차 목록은 새로 시작합니다. 합성 벤치마크 결과는 실제 GCP 처리량 보장이 아닙니다.

```bash
python -m scripts.benchmark_market_pipeline --cycles 5 --output performance-check-01.json
```

이 선택적 비교 명령은 임시 SQLite와 합성 입력을 사용하며 운영 DB·외부 API·LLM을 사용하지 않습니다.

## 고급: 이전 프로필의 과거 분봉을 재사용할 때

이 절차는 **기존 `realtime-paper`/RVOL 전략을 계속 운영·비교하는 경우**입니다. 권장 단순 전략을 처음 시작하는 사람의 필수 단계가 아닙니다. 기존 프로필은 최근 20개 정상장과 사이 조기 폐장일의 완전한 과거 분봉이 일일 운영 목록 선정에 영향을 줍니다.

엔진·별도 수집기를 중지하고 다른 원장으로 처음 한 번 복사합니다.

```powershell
python -m sessionquant prepare-paper --source-config config/sessionquant.candidates.example.yaml --config config/sessionquant.realtime-paper.example.yaml
```

`PREPARED`가 완료입니다. 과거 분봉과 시총 자료만 복사하며 최초 수신 시각을 유지합니다. 거래·포지션·엔진 상태·시작 요청은 복사하지 않고, 이미 준비한 대상을 덮어쓰지 않습니다. 같은 `universe_path`가 필요하고 환경변수로 두 원장을 같은 namespace에 강제하면 거부합니다. DB 전체 이전은 [GCP 이전 절차](GCP_PAPER.md#고급-기존-db-이전)를 사용합니다.

다음 명령은 과거 자료를 명시적으로 보충하는 선택적 작업입니다. API를 사용하므로 엔진을 중지한 상태에서 실행합니다.

```powershell
python -m sessionquant history-backfill --config config/sessionquant.realtime-paper.example.yaml
python -m sessionquant history-status --config config/sessionquant.realtime-paper.example.yaml --details --output history-legacy-01.json
```

이전 프로필의 예열은 완전한 종목·거래일의 검사를 해시·달력·검사 버전으로 재사용합니다. 끝까지 조회해도 누락·충돌이 남은 구간은 내용이 같으면 6시간 재조회를 생략하며, 누락을 정상으로 인정하지 않습니다. 오류·호출 한도 등으로 끝내지 못한 구간에는 적용하지 않습니다. DB 변경, 달력·검사 버전 변경, 6시간 경과 시 다시 검사합니다. 수동 `history-backfill`은 이 대기 기록을 사용하지 않습니다.

이전 REST 프로필의 종목/SPY 두 시점 비교, 호가용 요청 시간 예약, 필수 RVOL·시장 필터, 최대 집중 20개는 그 프로필의 정책입니다. 현재 권장 웹소켓 프로필의 동작과 섞어 해석하지 않습니다. [후보 선정 상세](archive/stages/STAGE08_CANDIDATES.md)는 이전 단계의 설계 기록입니다.
