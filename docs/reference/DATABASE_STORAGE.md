# 저장 데이터와 예상 용량

DB가 무엇을 저장하고 디스크가 왜 커지는지 확인할 때 읽습니다. 수치는 용량 계획 예이며 현재 서버의 남은 공간을 보장하지 않습니다. 실제 점검·백업은 [GCP 운영 안내](../GCP_PAPER.md)와 함께 봅니다.

[문서 목록](../README.md) · [매매 흐름](../TRADING_PROCESS.md) · [용어 설명](../GLOSSARY.md)

MySQL 8은 로컬 PC 또는 GCP VM 안의 DB 컨테이너에서 사용합니다. 연결 계정·비밀번호는 환경변수로 제공하고 소스나 GitHub에 저장하지 않습니다. 이 문서의 용량은 저장 구조와 합성 데이터의 JSON 바이트를 바탕으로 한 계획값이며, 사용자 PC의 실제 MySQL 사용량을 측정한 결과는 아닙니다.

## 어떤 데이터가 저장되는가

| 분류 | 저장하는 내용 | 누적 방식 |
|---|---|---|
| 시세 관측 | 조회한 현재가, 매수·매도 호가와 수량, 제공 시각·수신 시각 | 관측 시점별로 누적 |
| 1분봉 | 시가·고가·저가·종가·거래량, 봉 종료·수신 시각 | 종목·시각별로 누적 |
| 후보 종목 | 집중 선정·전략 조건, 최근 가격, 관찰·차단 사유 | 종목별 최신 상태 갱신 |
| 뉴스·공시 | 뉴스 ID, 관련 티커, 제목·본문, 출처·원문 링크, 발표·수신 시각 | 새로운 원문·버전 수신 시 저장 |
| AI 분석 | 사건·확정 여부, 호재·악재·혼합·불명확, 원문 근거, 희석 위험, 모델·토큰·분석 시각 | 논리적으로 다른 분석 결과 저장 |
| 매매 | 전략 신호, 주문·취소 상태, 실제 또는 모의 체결, 수량·가격·수수료·사유 | 주문은 최신 상태, 체결·신호는 이력 |
| 운영·복구 | 현재 보유·잔고, 일일 손실·수동 중지, 경고·오류, 소비한 입력 위치, 중복 주문 방지 정보 | 최신 복구 상태 갱신과 로그 이력 |

현재 구조에서 뉴스 분석은 원문 이벤트도 포함합니다. 따라서 같은 본문이 뉴스 기록과 분석 기록에 들어갈 수 있습니다. 토큰 비용 계산을 위해 LLM에 보내는 본문은 제한하지만, 그 제한이 저장된 SEC 원문 전체의 길이를 뜻하지는 않습니다. 수백 KB 공시가 많으면 뉴스 부분이 시세보다 더 커질 수 있습니다.

API 키·시크릿·OAuth 토큰·MySQL 비밀번호는 데이터베이스의 매매 기록으로 저장하지 않습니다. 실제 주문 모드에서는 복구를 위해 선택한 계좌 식별자와 주문·체결 내역을 저장합니다.

## 용량을 계산하는 예 — 현재 기본 설정과 다름

다음은 **20종목 관측, 보유 최대 5종목, 정규장 6.5시간, 월 22거래일**을 가정한 계획 예입니다. 추천 프로필의 감시 50개·집중 10개 및 WebSocket 수신량을 측정한 결과가 아닙니다. 보유가 5개라는 이유로 5개 데이터만 저장하는 것은 아닙니다. 후보에 대한 시세·공시·분석도 저장합니다.

계산에서 사용하는 주기는 설정의 대기시간이 아니라 실제 수신·저장 간격입니다. REST 요청 처리 시간이 추가되면 실제 저장 빈도는 설정값보다 낮을 수 있고, 별도의 실시간 생산자가 더 많은 이벤트를 공급하면 높을 수도 있습니다.

| 항목 | 실제 저장 간격 10초일 때 하루 건수 | 계획용 평균 JSON 크기 | 하루 원문 JSON |
|---|---:|---:|---:|
| 현재가 관측 20종목 | 46,800 | 250바이트 | 약 11.7MB |
| 호가 관측 7종목: 보유 5 + 순환 후보 2 | 16,380 | 300바이트 | 약 4.9MB |
| 완성 1분봉 20종목 | 최대 7,800 | 250바이트 | 약 2.0MB |
| 합계 | 약 71,000 | — | 약 18.6MB |

기존 합성 DB에서 측정한 평균은 호가 JSON 223바이트, 1분봉 186바이트, 주문 317바이트, 체결 208바이트였습니다. 실제 현재가 관측 예시는 177바이트였습니다. 위 표는 조금 큰 크기로 올려 잡은 값입니다. MySQL의 JSON 저장 형식·행·인덱스·페이지 여유 공간은 이 원문 바이트와 다릅니다.

뉴스 100건/일, 본문 평균 50KB를 추가로 가정하면 본문이 뉴스와 분석에 각각 들어가는 것만으로 약 10MB/일이 더해집니다. 본문 평균 500KB라면 같은 100건도 약 100MB/일입니다. 긴 공시의 개수와 본문 크기가 주요 변수입니다.

초기 소규모 운용은 **테이블과 인덱스 합계 약 0.5~3GB/월**을 예산으로 잡고 실제 사용량을 확인하는 방식이 적합합니다. 위의 20종목·10초 관측과 적당한 뉴스량에서는 약 **30~100MB/거래일** 수준이 계획 범위지만, 큰 공시가 많으면 이를 넘을 수 있습니다. 이 수치는 보장 상한이 아닙니다.

비슷한 자료를 실제로 1초마다 저장하면 시세 원문만 약 168MB/일, 약 3.7GB/22거래일입니다. 행·인덱스와 뉴스를 포함하면 수 GB에서 10GB 이상/월로 커질 수 있습니다. 모든 거래소의 모든 체결 틱이나 전체 시장 데이터를 저장하는 구성은 이 계산에 포함하지 않았습니다.

## 중복 분석과 상태 저장

같은 공시를 1분마다 조회한다고 본문을 매번 새로운 분석으로 누적해서는 안 됩니다. 예를 들어 20종목 × 최근 공시 3개 × 390회 조회 × 본문 100KB이면 본문 사본만 약 **2.34GB/일**입니다. 동일 원문·티커·모델·프롬프트·결과 상태의 논리 분석을 구분하고 중복 저장을 줄여야 하는 이유입니다. 실패·키 누락·규칙 분류도 예외가 아닙니다. 모델이나 원문·분석 결과가 실제로 달라진 경우의 이력은 필요합니다.

엔진의 현재 상태와 제어값은 한 상태를 갱신하므로 매번 새 행이 생기지는 않습니다. 다만 상태에는 현재 뉴스 근거, 보유, 주문·체결 복구 정보가 포함됩니다. 오래된 뉴스 문맥은 제한하더라도 주문 식별자·체결 대사 정보를 용량 때문에 임의로 버리면 중복 주문 방지가 깨질 수 있습니다.

MySQL 바이너리 로그는 별도입니다. 큰 JSON 상태를 계속 갱신하면 테이블의 최종 크기는 작아도 변경 로그의 합계는 훨씬 커질 수 있습니다. 따라서 **DB 테이블 크기 = MySQL 전체 디스크 사용량**은 아닙니다. 바이너리 로그·redo/undo·임시 공간·백업 복사본과 저장소의 여유 공간을 따로 고려해야 합니다. 처음에는 10~20GB 이상의 여유 공간을 확보하고 실제 증가량을 확인하는 편이 좋으며, 이것도 보장 상한은 아닙니다.

## 현재 보관 정책과 별도 계획 예

추천 strategy-lab 설정은 `retention.enabled: true`, 진단 7일·뉴스 30일·한 번에 최대 90초의 정리 정책을 지정합니다. 실제 삭제는 GCP 종료 절차에서 최근 클라우드 백업 성공 기록을 확인한 뒤 제한된 항목에 적용합니다. 설정만으로 모든 자료가 매일 삭제되거나 파일 크기가 줄어드는 것은 아닙니다. 주문·체결·비용·복구 제어·RVOL 이력·재생 입력은 보호하며, 매매 근거로 사용한 뉴스도 보존합니다. 구현은 [retention.py](../../sessionquant/database/retention.py)를 참고하세요.

아래는 별도로 정할 수 있는 용량 계획 예이며 현재 자동 정책 또는 법정 보관 기간을 뜻하지 않습니다.

| 데이터 | 운영 예시 |
|---|---|
| 현재가·호가의 세부 관측 | 7~30일 |
| 완성 1분봉 | 90일 이상, 검증 기간에 따라 연장 |
| 뉴스·AI 분석 | 90일 이상. 실제 거래의 판단 근거는 더 오래 보관하거나 별도 보관 |
| 주문·체결·손익·중복 방지·위험 알림 | 기본 자동 삭제 대상에서 제외 |
| 현재 포지션·복구·일일 중지 상태 | 운영 중 삭제 금지 |

정리 기능은 먼저 대상·건수를 미리 확인하고 필요한 경우에만 실행합니다. 자동 보관 정책을 켜지 않으면 데이터는 계속 늘어납니다. 행을 삭제해도 InnoDB 파일이 즉시 작아져 운영체제의 빈 공간으로 반환되는 것은 아닙니다. 확보한 페이지를 이후 입력에 재사용하는 경우가 있으므로, 삭제한 행 수와 디스크 반환량을 같은 값으로 해석하지 않습니다.

현재 [GCP Compose](../../deploy/gcp/compose.yaml)는 `--skip-log-bin`을 지정합니다. 이미 실행 중인 DB가 이 옵션을 적용했는지는 별도로 확인해야 하며, 기존 로그가 설정 파일 수정만으로 제거되지는 않습니다. 압축 백업 크기는 원본 DB·인덱스·작업 공간 크기와 다릅니다.

## 실제 용량 확인

MySQL Workbench에서 다음 조회로 테이블·인덱스 사용량을 확인할 수 있습니다. 데이터베이스 이름을 바꿨다면 `sessionquant`도 바꾸세요. 예전 `PQ_` 설정을 쓰는 DB는 `pennyquant`일 수 있습니다.

```sql
SELECT
    TABLE_NAME,
    TABLE_ROWS AS estimated_rows,
    ROUND(DATA_LENGTH / 1024 / 1024, 2) AS data_mb,
    ROUND(INDEX_LENGTH / 1024 / 1024, 2) AS index_mb,
    ROUND((DATA_LENGTH + INDEX_LENGTH) / 1024 / 1024, 2) AS total_mb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'sessionquant'
ORDER BY DATA_LENGTH + INDEX_LENGTH DESC;
```

InnoDB의 `TABLE_ROWS`는 추정치입니다. 프로그램의 실제 건수·JSON 바이트 통계와 함께 보고, 일주일 정도 운용한 뒤 하루 증가량 × 원하는 보관 기간으로 다시 산정합니다. 외부 저장한 JSONL 수집 파일·보고서·DB 백업은 위 테이블 조회에 포함되지 않습니다.
