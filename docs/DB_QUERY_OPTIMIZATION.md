# 큰 JSON 조회를 줄이는 DB 개선

목록에 필요한 작은 값은 별도 요약·색인에서 읽고, 전체 본문은 상세 확인이나 보존 판단에 필요할 때 읽습니다. 주문·체결 장부와 당시 판단의 원본은 유지합니다.

## 확인한 병목과 개선 범위

운영 서버의 2026-11-26 정리 보고서에서는 연구 기록 본문 조회가 약 2,302초, 키 조회가 약 0.8초, 삭제가 약 23초였습니다. 본문 조회에서 복구된 시간 초과도 108회 있었습니다. `COMPLETE`는 정리 완료를 뜻하며, 도중의 재시도까지 없었다는 뜻은 아닙니다.

과거 연구 기록 한 건은 약 2,296 KiB였고 그중 `news_contexts`가 약 2.1 MiB였습니다. **한 건의 비중을 DB 전체 비중으로 해석하지 않습니다.** 테이블·인덱스 통계도 MySQL 파일 전체의 실제 사용량과 다릅니다.

| 단계 | 변경 | 유지하는 기준 |
| --- | --- | --- |
| 1. 반복 본문 조회 줄이기 | 처리 기록은 최근 최대 100건의 작은 요약을 사용합니다. 정리 후 잔여량·생성량 확인은 유효한 보관 메타데이터를 재사용합니다. | 요약이 없거나 오래됐으면 해당 원본만 확인합니다. 확인이 끝나지 않으면 `UNKNOWN`을 유지합니다. |
| 2. 검색 조건 색인화 | 실제 AI 요청 여부를 작은 열에 저장하고 `(namespace, network_attempted, source_seq)` 색인으로 찾습니다. | 모든 원본 행의 색인 준비를 증명한 뒤 사용합니다. 최근 일부 행만 잘라서 오래된 요청을 누락하지 않습니다. |
| 3. 기존 DB 준비 | 휴장·폐장 후 작은 묶음으로 기존 행의 요약·색인을 채우고 검증합니다. | 시간 한도에서 중단·재개하며, 준비 완료 전에는 기존 조회를 사용합니다. 이 작업은 자료를 삭제하지 않습니다. |

신규 뉴스 중복 저장은 이미 운영 프로필의 `bounded_diagnostics`와 `news_diagnostic_v1`로 제한합니다. 이번 작업에서 뉴스 원문·분석을 다시 잘라내지 않습니다. 보관량·보호 대상은 [저장 기준](DATA_STORAGE.md)을 참고하세요.

## 구조를 이렇게 나눈 이유

- `pq_pipeline_status.payload`는 원본입니다. `sq_pipeline_summary`에는 목록 표시용 값만 저장하며 긴 문자열은 제한하고 종목별 상세 배열은 넣지 않습니다.
- `pq_llm_calls.payload`는 호출 감사 기록입니다. `sq_llm_attempt_index`에는 원본 키·namespace·수정 시각·버전·실제 요청 여부만 저장합니다.
- `sq_research_retention_meta`는 기존 보관 판단 메타데이터입니다. 원본 키·namespace·수정 시각·버전이 맞을 때 재사용합니다.

새 요약·색인은 원본 INSERT·UPDATE와 같은 트랜잭션에서 트리거로 유지하고, 원본 삭제 시 외래 키로 함께 정리합니다. 롤백하면 원본과 파생 값이 함께 되돌아갑니다. 설치만으로 과거 전체 본문을 읽거나 다시 쓰지 않습니다.

이는 조회에 자주 쓰는 부분을 분리하는 변경입니다. 뉴스·주문 근거 전체를 한꺼번에 정규화하면 과거 시점의 분석 버전과 원문을 연결하고 보호·복원하는 방식도 바뀝니다. 현재 확인된 병목을 줄인 뒤, 중복량과 실제 조회 비용을 다시 측정해 그 범위를 결정합니다.

LLM 색인은 `recent_llm_attempts()`를 사용하는 처리 현황·진단 조회에 적용됩니다. 별도 감사 상세 화면의 전체 호출 기록 조회까지 모두 이 색인을 사용하는 것은 아닙니다. 트리거 정보를 볼 수 없는 제한 계정은 기존 조회로 돌아갑니다.

## 운영 DB에 준비하기

먼저 이 변경을 포함한 코드와 컨테이너가 정상 배포됐는지 확인합니다. GitHub 병합만으로 기존 DB의 색인 준비가 완료되지는 않습니다. 일반 런타임 초기화는 보조 테이블·트리거를 설치하지만, 점검 화면은 읽기 전용 연결을 사용하므로 명시적 준비가 필요합니다.

1. Windows에서 `Win + R` → `cmd` → Enter 후 접속합니다.

   ```bat
   gcloud compute ssh sessionquant-paper --project=sessionquant --zone=us-central1-a --tunnel-through-iap
   ```

2. PuTTY의 `@sessionquant-paper`에서 휴장·정규장 마감 후, 매매 종료와 보유·미체결 없음이 확인된 상태에서 실행합니다. 정상적인 점검 배포 직후 사용할 수 있습니다.

   ```bash
   sudo bash /opt/sessionquant/deploy/gcp/prepare_db_projections.sh --apply
   ```

3. 한도 안에 준비가 끝나지 않으면 같은 명령을 다시 실행합니다. 완료한 묶음 다음부터 이어가며, 완전성 검증이 끝난 색인은 다시 본문 전체를 보충하지 않습니다.

   ```bash
   sudo cat /var/lib/sessionquant/health/db-projections-last.json
   ```

   `COMPLETE`는 요약·색인 준비 완료, `PENDING`은 제한 안에서 일부 진행, `FAILED`는 사전 조건·설치·연결 확인이 필요하다는 뜻입니다. 자료 정리의 완료 상태와는 다른 보고서입니다.

이 명령은 매매 런타임이 실행 중이거나 유지보수 잠금이 사용 중이면 중단합니다. 조회용 점검 대시보드는 허용합니다. DB의 `read_only` 또는 `super_read_only` 상태를 임의로 해제하지 않습니다. 야간 백업 뒤 쓰기 금지 상태라면 기존의 검증된 업데이트 절차로 돌아가세요. 보조 테이블 준비도 DB 변경이므로 백업 재사용 증명이 그대로 유지된다고 가정하지 않습니다.

준비 컨테이너의 종료 자체를 확인하지 못한 경우에는 `FAILED`와 `projection-preparation-blocked` 표시를 남겨 다음 시작·업데이트·마감·단독 백업을 차단합니다. 보고서와 해당 컨테이너의 종료 여부를 확인한 뒤 복구해야 하며 차단 파일부터 지우지 않습니다.

준비 시간은 기본 60초이며 `--seconds 120`처럼 최대 300초까지 지정할 수 있습니다. SQL 조회·잠금 대기에도 별도 제한을 두지만 DB의 실제 취소가 즉시 끝난다는 보장은 없으므로 호스트 작업 한도도 함께 적용합니다. `--restart`는 LLM 색인을 첫 행부터 다시 보충·검증해야 할 때만 사용합니다.

파생 테이블을 직접 수정했다면 완료 기록을 믿고 검사만 반복하지 않습니다. LLM 색인을 **무효화 → 처음부터 보충 → 완전성 재검증**해야 합니다. 원본·파생 값을 수동으로 바꾸는 운영 방식은 권장하지 않습니다.

## 배포 뒤 확인할 결과

| 확인할 것 | 개선을 판단하는 근거 |
| --- | --- |
| 시스템·설정 처리 기록 | 첫 조회·페이지 전환 소요 시간, 최근 100건의 기존 표시 값 유지 |
| 뉴스 처리 현황의 실제 AI 요청 | 준비 완료 여부, 누락 없이 같은 기록을 표시하는지 |
| 자료 정리 | `timings`의 `PAYLOAD`, `BACKLOG_PAYLOAD`, `GENERATION_PAYLOAD` 비용과 시간 초과, 메타데이터 재사용 건수 |
| 정리 완료 여부 | `COMPLETE`, 잔여 `CLEAR` 여부를 각각 확인. `UNKNOWN`은 0건이 아님 |
| 다음 백업 | DUMP·검증·업로드 각각의 시간, 최종 압축 파일 크기 |
| 저장 공간 | 논리 삭제 건수와 `du`의 물리 파일 크기를 구분 |

과거 JSON 중 보관 메타데이터가 없는 자료는 처음 검사할 때 여전히 본문을 읽어야 합니다. 필요하면 [기존 밀린 자료 정리 절차](GCP_PAPER.md#밀린-자료를-폐장-후-정리하기)를 사용합니다. 요약·색인 준비는 그 삭제 작업의 대체가 아닙니다.

이 변경은 `OPTIMIZE TABLE`, 전체 테이블 재작성 또는 디스크 파일 강제 축소를 수행하지 않습니다. 로컬 합성 자료와 격리 MySQL 검사는 결과 일치·인덱스 사용·원자성·중단 복구를 확인합니다. 운영 서버의 실제 속도와 모든 시간 초과 해소 여부는 배포 후 기록으로 검증합니다.

## 격리 MySQL에서 확인한 조회 효과

MySQL 8.4·256 MiB 버퍼 풀에서 각 경로를 예열한 뒤 5회 실행한 중앙값입니다. 운영 DB와 연결하지 않았고 시험 자료는 별도 namespace에서 제거했습니다.

| 합성 자료 | 기존 조회 | 개선 조회 |
| --- | ---: | ---: |
| 처리 기록 40건, 원본 각 약 1.5 MB | 12.106 ms | 2.471 ms |
| AI 호출 이력 10,020건, 실제 요청 20건 | 15.511 ms | 3.328 ms |

반환 결과는 일치했습니다. 처리 기록 원본 JSON 합계는 약 60 MB, 목록용 요약은 약 15 KB였습니다. 이는 문서 크기 비교이며 실제 디스크 읽기량 측정은 아닙니다. AI 요청의 실행 계획은 원본 10,020행 검사에서 색인 키 20개와 해당 원본 20건 조회로 바뀌었습니다. 개선 조회 시간에는 완료 기록·트리거 서명 확인 비용도 포함됩니다. 차가운 캐시나 GCP 동시 부하에서 같은 시간이 나온다는 뜻은 아닙니다.
